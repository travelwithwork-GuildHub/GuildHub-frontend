# remote-players Specification

## Purpose
別人在這個世界裡的存在與位置：誰在場、他們在哪、以及那些資料放在哪一層。

分層是這個 capability 最重要的部分，因為放錯層**不會有任何錯誤訊息** ——
`CONTEXT.md` 的原文是「違反這條不會有錯誤訊息，只會變慢」，
而規模是 40 人 × 10 Hz ＝ 每秒 400 次更新。

它也是 W1 里程碑「**看得到別人**」的那一項：做完之後畫面上會真的出現其他人。

## Requirements

### Requirement: 名單與動態分成兩個容器，動態不進 React

系統 SHALL 把遠端玩家的資料分成兩份：

- **名單**：每個人的 `id` 與身分資料（`name`、`av`）。
  這一份 SHALL 進 React —— join / leave 是低頻事件，而且它決定掛幾個元件。
- **動態**：每個人的座標與朝向。這一份 **MUST NOT 寫入 React state 或 Zustand**，
  只能放 ref。

渲染遠端角色的元件 MUST NOT 把座標或朝向當成 props 接收 ——
它只接收穩定的 `id`，在 render loop 裡自己去讀。

理由是 `CONTEXT.md` 的硬規則：**高頻資料不進 React**，
而**違反它不會有錯誤訊息，只會變慢**。`pos` 每秒 10 次 × 40 人 ＝ 每秒 400 次；
每一次都觸發 React 的協調，就是每秒 400 次重繪 40 個角色。

#### Scenario: [FE-R07-S01] 收到位置更新時，名單不會改變

- **WHEN** 名單已經建立，之後收到同一批人的位置更新
- **THEN** 動態資料改變了
- **AND** 名單的內容與其身分**完全沒有變**（連物件本身都沒有被換掉）

> 只斷言「名單內容相等」是不夠的：每次都建一個內容相同的新陣列，
> React 照樣會重繪。要驗的是**沒有產生新的名單**。

### Requirement: snapshot 建立名單，而且排除自己

收到 `snapshot` 時系統 SHALL 用它重建整份名單與動態。

**自己 MUST NOT 出現在遠端玩家裡。** 實測 `snapshot` 的 `players`
**包含自己**（第一個元素的 `id` 就是 `hello` 的 `you`）——
沒有排除的話，畫面上會有一個跟本地角色重疊、而且跟著它走的分身。

每個人的初始座標與朝向 SHALL 取自 `snapshot` 的內容。
**不可以等第一則 `pos` 才決定位置** —— 一個進來之後就沒動過的人
**永遠不會出現在 `pos` 裡**（靜止時後端整則不送）。

`snapshot` SHALL **清空每個人既有的樣本**，只留下它自己帶來的那一個 ——
它是權威狀態的重建，不是一段連續軌跡上的一點。
留著舊樣本的話，畫面會把**上一個 session 的位置**與新位置連成一段插值。

#### Scenario: [FE-R07-S02] snapshot 建立名單並排除自己

- **WHEN** 收到一則包含自己與另外兩個人的 `snapshot`
- **THEN** 名單裡有兩個人，**不含自己**
- **AND** 那兩個人的座標來自 `snapshot`，不是預設值

#### Scenario: [FE-R07-S03] 後來的 snapshot 取代整份名單

- **WHEN** 已經有名單，之後收到一則只含另一個人的 `snapshot`
- **THEN** 名單裡只剩那一個人
- **AND** 前一批人的動態資料也被清掉了

#### Scenario: [FE-R08-S18] snapshot 也清掉「仍然在名單裡」那個人的樣本

- **WHEN** 一個人有一段樣本歷史，正在畫面上移動
- **AND** 收到一則**仍然包含他**、但把他放在很遠處的 `snapshot`
- **THEN** 他的樣本只剩 `snapshot` 帶來的那一個
- **AND** 畫面上他直接在新位置，沒有從舊位置滑過去

> `FE-R07-S03` 只證明了「被移除的人消失」，證明不了「留下來的人被重設」——
> 而後者才是換場景之後把**上一個場景的位置**跟新位置連成一段插值的來源。

### Requirement: presence 的 join 與 leave 在同一則裡處理

`presence` **把 join 與 leave 合併成一則**（後端如此）。
系統 SHALL 在同一則裡處理兩者。

`leave` SHALL 是**原子的清理**：把那個人從**名單、樣本、以及任何其他
per-player 的容器**移除。只清一邊的話，沒清到的那一份會隨著連線時間累積 ——
而且同一個 id 之後再出現時會讀到舊資料。

`join` 帶著座標，它 SHALL 讓那個人**從那個位置開始**，
既有的樣本（如果有的話）SHALL 被清掉 —— 理由同 `snapshot`。

以下三種都 MUST NOT 造成錯誤或改變其他人的資料：
`leave` 一個不在名單裡的 id、`join` 一個已經在名單裡的 id、
以及 `join` 裡出現自己。

#### Scenario: [FE-R07-S04] 一則 presence 同時處理進場與離場

- **WHEN** 收到一則 `presence`，`join` 有一個新的人、`leave` 有一個現有的人
- **THEN** 名單裡多了新的那個、少了離開的那個
- **AND** 離開的那個人的動態資料也被清掉了
- **AND** 沒有被提到的人完全沒有受影響

#### Scenario: [FE-R07-S05] 不合常理的 presence 不得造成錯誤

- **WHEN** `leave` 一個不在名單裡的 id
- **THEN** 不拋錯，其他人的資料不變
- **AND WHEN** `join` 一個已經在名單裡的 id
- **THEN** 不拋錯，那個人不會出現兩次
- **AND WHEN** `join` 裡出現自己
- **THEN** 自己不會被加進遠端玩家

#### Scenario: [FE-R08-S11] 離開的人不留下樣本

- **WHEN** 一個有數十筆樣本歷史的人 `leave`
- **THEN** **存放樣本的容器裡不再有這個 id**（直接斷言容器，不是斷言畫面）
- **AND** 只 `leave` 一個人時，其他人的樣本一筆都沒少

> ⚠️ **不可以用「重新 `join` 之後不會從舊位置滑過來」來證明這一條。**
> `join` 自己就會清空樣本，所以就算 `leave` 完全忘了清，那樣的測試照樣是綠的 ——
> 而漏掉的是一個**沒有錯誤訊息的記憶體洩漏**。

#### Scenario: [FE-R08-S17] join 一個已經在名單裡的人，樣本要重來

- **WHEN** 一個人已經有樣本歷史（**沒有先 `leave`**）
- **AND** 收到一則 `join` 裡有同一個 id、座標在很遠的地方
- **THEN** 他的樣本被清空，只剩 `join` 帶來的那一個
- **AND** 畫面上他直接在新位置，沒有從舊位置滑過去

### Requirement: pos 只更新已知的人，並在寫入時就換算成世界座標

收到 `pos` 時系統 SHALL 為對應的人**追加一個帶時間的樣本**
（座標、朝向，以及寫入當下的時間），MUST NOT 直接覆寫他在畫面上的位置。
畫面位置由 `remote-interpolation` 從樣本求值。

寫入樣本時的時間 SHALL 來自那個**注入的單調時間來源**，
與求值畫面位置用的是同一個。

**不在名單裡的 id SHALL 被忽略**，MUST NOT 因此建立一個新的人 ——
名單只由 `snapshot` 與 `presence` 決定。`pos` 是差量，不是名單來源。

協定的整數像素 SHALL 在**寫入的時候**換算成世界座標，
**MUST NOT 留到 render loop 每一幀換算**。換算規則來自 `world-coordinates`，
MUST NOT 在這裡重寫。

#### Scenario: [FE-R07-S06] pos 更新已知的人，忽略不認識的 id

- **WHEN** 收到一則 `pos`，其中一個 id 在名單裡、另一個不在
- **THEN** 在名單裡的那個人多了一個樣本，內容是世界座標與朝向
- **AND** 不在名單裡的那個 id **沒有**被加進名單
- **AND** 存起來的是世界座標，不是協定的整數像素

#### Scenario: [FE-R08-S10] pos 是追加樣本，不是覆寫位置

- **WHEN** 同一個人連續收到兩則 `pos`
- **THEN** 兩個位置都留著，形成一段可以插值的區間
- **AND** 第二則到達的當下，畫面位置**還在第一則附近**，不是直接跳到第二則

### Requirement: 名單上的每個人都在畫面上有一個角色

系統 SHALL 為名單上的每一個人渲染一個角色，並在 render loop 裡
把該角色的位置與朝向設成**從樣本求值出來的**畫面位置與朝向。

角色 SHALL 重複使用既有的程式化 Chibi 角色，MUST NOT 另做一套。

render loop 在讀取一個人的樣本之前 SHALL 確認那份樣本還在 ——
`leave` **同步**清掉 `motion` 的 entry，而角色要等 React 依新名單重繪
才會卸載，中間有一段「元件還在、樣本已經沒了」的空窗。

> ⚠️ **原本這裡寫的是「確認角色物件還在 —— 卸載與 render loop 之間有競態」，
> 那是錯的。** 量過：元件卸載之後它的 `useFrame` **完全不再被呼叫**，
> 而且 ref 從來沒有是 `null` 過（連第一幀都不是）。React 的 commit 是同步的，
> rAF 不會插進它中間，所以「元件還掛著但 ref 是 null」在這個結構下不可達。
> 那個 null 檢查是 **TypeScript 的型別收斂**（`useRef<Group>(null)` 是 `Group | null`），
> 不是執行期防禦 —— 拿掉它不會變紅，只會編譯不過。
> **真正可達、而且需要被釘住的是上面那個空窗。**

**位置與朝向 MUST NOT 成為 React 的 props 或 state**：
它們每秒改變 60 次 × 名單人數。這條限制在插值之後**更嚴格了**，
因為現在連「沒有新樣本」的那些幀也在改變畫面位置。

#### Scenario: [FE-R07-S07] 名單改變時，畫面上的角色跟著增減

- **WHEN** 名單上有兩個人
- **THEN** 畫面上有兩個遠端角色
- **AND WHEN** 其中一個離開
- **THEN** 畫面上只剩一個遠端角色

#### Scenario: [FE-R07-S08] 遠端角色的位置來自動態資料，不是 props

- **WHEN** 一個遠端角色已經在畫面上，之後多了一個新樣本
- **THEN** 下一次 render loop 之後，那個角色的位置**等於用當下游標求值的結果**
- **AND** 過程中**沒有發生任何 React 重繪**

> ⚠️ **舊的寫法（「位置變成新的值」）在插值之後是錯的。**
> 因為有 250 毫秒的 render delay，新樣本剛到時畫面**本來就不應該**
> 立刻變成新位置。照舊寫法實作會得到一個「跳格但測試全綠」的正式碼。

#### Scenario: [FE-R08-S12] 插值的每一幀都改變 transform，而且都不觸發 React 重繪

- **WHEN** 一個遠端角色正在兩個樣本之間移動
- **AND** 推進數十幀
- **THEN** 角色的 transform **每一幀都不同**（真的在動）
- **AND** 承載遠端角色的元件重繪次數維持不變

> ⚠️ **只斷言「沒有重繪」是空的** —— render loop 什麼都不做時它也是綠的。
> 兩個斷言要放在同一條裡。

#### Scenario: [FE-R08-S19] 寫入與求值用的是同一個注入時鐘

- **WHEN** 注入一個**假的**時間來源，用它寫入兩個相距 100 毫秒的樣本
- **AND** 只推進那個假時鐘，真實時間完全不動
- **THEN** 畫面位置跟著假時鐘前進
- **AND** 在假時鐘推進 `RENDER_DELAY` 之後，位置正好是第二個樣本

> ⚠️ 這一條抓的是「樣本用注入的時鐘、求值卻自己去拿 `performance.now()`」。
> 那樣寫的話真實時間不動，畫面就永遠停在第一個樣本 —— 而在**正式環境**
> 兩個時鐘剛好都在走，所以看起來像是對的。**沒有這一條，那個 bug 只會在
> 真實網路的某些時序下才現形。**

#### Scenario: [FE-R08-S20] 樣本已經被清掉，但角色還沒卸載

- **WHEN** 一個遠端角色已經在畫面上、而且 transform 已經被寫過
- **AND** 他的樣本被就地刪掉（`leave` 做的事），**但名單還沒重繪**
- **THEN** 下一幀不拋錯
- **AND** 角色的 transform 停在原地，**不寫入任何新值、也不跳回原點**

> ⚠️ **不可以用「把角色卸載掉再推進幾幀」來測這一條。**
> 卸載之後那個元件的 `useFrame` 根本不會再被呼叫，所以那樣的測試
> **就算把守衛整條拿掉也是綠的** —— 它驗的是 R3F 的訂閱管理，不是我們的程式碼。
> 要製造的是**資料突變與 React 重繪之間的時序差**：只改 Map，不動名單。

### Requirement: 自己永遠不會出現在遠端玩家裡

後端**不做逐人過濾** —— 廣播就是廣播給 scene 裡的每一條連線，包含送出者自己。
實測（打自己起的本機後端）：

```
送  {"t":"move","x":320,"y":640,"f":2}
收  {"t":"pos","p":[["u-same",320,640,2]]}      ← 自己的 id
```

系統 SHALL 保證**自己的 id 永遠不會成為一個遠端角色**。

⚠️ **這是結構性保證，不是一個過濾器。** 它不是靠在 `pos` 的迴圈裡寫
`if (id === selfId) continue` 達成的，而是靠**自己從來沒有進過名單**：

- `snapshot` 建名單時跳過 `selfId`
- `presence.join` 也跳過 `selfId`
- `pos` **只更新名單裡已經有的人**，不會替不認識的 id 建立新的

三條缺一條，自我回聲就會長出一個分身。**維持這三條的方式是不要在
`pos` 那裡補一個過濾器** —— 補了之後前兩條就可以被安全地拿掉，
而拿掉的症狀要到別人重構名單時才會爆。

`selfId` 來自 `hello.you`。它 MUST NOT 放進 React state ——
處理 `snapshot` 的當下必須同步讀得到它。放進 state 的話，
`hello` 與 `snapshot` 在同一批事件裡到達時，處理 `snapshot` 時讀到的可能還是舊值。

> **為什麼一個分身特別難發現**：它跟本人完全重合、而且跟著本人走。
> 單人測試時畫面上看不出有兩個角色；要兩個人同時在場、而且從別人的視角看，
> 才會看到「那個人身上疊著另一個人」。

#### Scenario: [FE-R05-S01] 自己的位置原路廣播回來時不產生分身

- **WHEN** 已經有一份含自己與另一個人的名單
- **AND** 收到一則 `pos`，裡面**同時**有自己的 id 與那個人的 id
- **THEN** 自己**沒有**被加進遠端玩家的名單
- **AND** 存放樣本的容器裡**沒有**自己的 id
- **AND** 另一個人的位置**照常**更新 —— 自我回聲不得讓整則訊息被丟掉

#### Scenario: [FE-R05-S02] snapshot 裡的自己不會變成遠端角色

- **WHEN** 收到一則 `snapshot`，第一個元素就是自己（**實測後端如此**）
- **THEN** 名單裡沒有自己
- **AND** 存放樣本的容器裡也沒有自己

#### Scenario: [FE-R05-S03] selfId 還沒設定時不得把自己當成別人

- **WHEN** `selfId` 尚未從 `hello` 取得（值是 `null`）
- **AND** 在這個狀態下收到一則含自己的 `snapshot`
- **THEN** 自己會被當成遠端玩家 —— **這是已知且無法在這一層擋掉的**
- **AND** 因此 `hello` SHALL 在同一條連線上早於 `snapshot` 被處理，
  而這條測試存在的目的是**把那個前提釘住**：一旦有人改成非同步設定
  `selfId`、或把它放進 React state，這條就會紅

> ⚠️ **這一條刻意斷言「壞掉的行為」**，因為它描述的是這一層的**邊界**。
> 把它寫成「就算 `selfId` 是 null 也不會有分身」是做不到的 ——
> 這一層沒有別的資訊可以認出自己。真正的防線是「`hello` 先到、而且同步設定」，
> 所以測試要釘的是那個前提，不是一個假裝擋得住的行為。
