## Context

動機見 `proposal.md`〈Why〉。

**現況**：`FE-R01`（已封存）把非 `hello` 的訊息**原樣交出去**，現在沒有人接。
`api-contract`（已封存）有 `ServerMessage` 的 discriminated union。

**這一項的規模很小**（WBS 5 點），但它決定的是**信任邊界**：
下游三項會不會各自再寫一次判斷，取決於這一層交出去的東西夠不夠好用。

## Goals / Non-Goals

範圍邊界見 `proposal.md`〈不做什麼〉。

**Goals**
- 讓下游拿到的每一則都是**驗證過的**，不必自己 `JSON.parse`。
- 讓「協定變了」在開發時就大聲炸開。

**Non-Goals**
- 不做分派、不做錯誤 UI、不碰連線狀態機。
- **不宣稱違規一定會被處理** —— 見 D1。

## Decisions

### D1. 必填的違規通報，而且明文寫它保證不了什麼

兩位審查者對「未知 `t` 明顯失敗」的處置意見不同：

| | 主張 |
|---|---|
| Gemini 3.1 Pro | 只回傳 result；**呼叫端必須 throw**。必填回呼是「自我安慰」 |
| codex gpt-5.6-terra | result **加**必填回呼，但**不可宣稱它防止得了忽略** |

**選 codex 的**，兩個理由：

1. Gemini 的「呼叫端 throw」跟這一份規格的另一條（訊息級失敗不影響其他訊息）
   有張力 —— 而且它依賴一個**還不存在的**全域 error boundary。
2. Gemini 說必填回呼是自我安慰，**那句話是對的**，但結論下錯了：
   正確的做法不是拿掉它，是**把它保證不了的東西寫進規格**。

所以：必填回呼保留，價值是**逼呼叫端在組裝的地方明確表態**；
規格同時明文寫「傳一個空函式就等於靜默忽略，型別擋不住」。

這正是 `AGENTS.md` 那句話的用法 —— **高估一個閘門比沒有它更危險**。

### D2. 不區分「後端送錯」與「契約更新」

對一個正在執行的舊版客戶端而言，兩者可安全處置的方式完全相同：
它不認得那則訊息，也不能把它當成合法資料。

替「未來的契約更新」留一條寬鬆的路，等於讓**開發時**也不會炸 ——
而那正是唯一有人會看到它的時機。

### D3. 驗證失敗就丟掉，不往下游傳

驗證層唯一的價值是建立信任邊界。放行一則壞掉的訊息，
下游三項就都得自備防禦性程式碼，而這一層就形同虛設。

## Risks / Trade-offs

- **呼叫端可以傳一個空函式** → 已在 D1 與 Requirement 明文寫出來。
  沒有機器擋得住，只有 review。
- **這一層只驗形狀，不驗語意** → 例如 `pos` 裡的 id 是不是真的存在，
  這一層不知道。那是 `FE-R07` 的事。
- **`api-contract` 的 schema 太鬆的話這一層也跟著鬆** → 那是同一份契約，
  刻意的：**只有一個地方定義形狀**。
