# FE-W12 互動物件 —— 設計

開工前把四個分歧點送 codex `gpt-5.6-sol` 與 Antigravity `Gemini 3.1 Pro`
互審三輪（把 A 的答案餵給 B 打）。**兩邊在第三輪都寫了「我同意這份草稿可以合併」。**
過程中有四次立場改變，四次都留在下面 —— 誰改的、為什麼改。

## D0：範圍先修，再寫規格

`Seat` 原本在這一項的 WBS 逐字裡。座位的 API 是
`GET /api/projects/{project_id}/seats`，**綁專案**，而 Guild Hall 是 `lobby`，
不屬於任何專案。

codex 的處置逐字：

> 因此要先用 `governance/` PR 修正 WBS。**不能只在 `FE-W12` proposal 裡自行省略
> `Seat`**，否則 proposal 直接違反當前 WBS。

已完成（PR #212）：移到 `FE-W16 Project Room`，4 點。
`FE-W12` **維持 12 點** —— 拿掉 Seat 之後，API 狀態機、輪詢生命週期、
標籤投影與四條新判準本來就沒有被原本的估算涵蓋。

## D1：今天沒有後端，那「依 API 生成」怎麼算做到

我送出去的前提是「**今天在任何環境下 `listRooms()` 都拿不到資料**」。
**codex 指出這個前提是錯的**：

> `guildhub` 在開發者本機可用；而受控的瀏覽器驗收環境也可以攔截其 HTTP 回應。
> **真正缺少的是「可供線上展示的後端」，不是「無法驗證成功路徑」。**

所以：真的呼叫 `listRooms()`，成功路徑的人工驗收用 Playwright 攔截
`/api/rooms` 回固定 fixture。

⚠️ **截圖必須註明「受控 API fixture」。** 它證明的是「元件在收到這份資料時會
生成這些門」，**不是**「線上整合可用」。三件事要分開記錄：

| 主張 | 誰能證明 |
|---|---|
| 元件的成功／失敗行為 | 受控瀏覽器環境 |
| 真 GuildHub 整合 | 只有連得到後端的本機環境 |
| Vercel 上可用 | **今天不能宣稱** —— 那是部署依賴 |

⚠️ **`internal` adapter 攔截不到**：它在**送出請求之前**就拋
`AdapterNotImplementedError`（那是 `FE-O02-S02` 明文要求的）。
所以驗收必須跑在 `guildhub` adapter 上。

**沒有選「不接 API、門用靜態配置」**：那樣就確定沒有完成這一項的核心要求。
**也沒有選「順手做一個 Route Handler」**：那侵入 `FE-O03`（W2，8 點，規格未寫）。

## D2：名稱與在線數 —— DOM overlay，不是 3D 文字

`FE-W10` 把這一題留給這裡，並且明文「要在 3D 畫字的話**必須另外修改資源所有權契約**，
不得偷渡進來」。

**沒有改那份契約。** 三條 3D 路（troika／drei／`CanvasTexture`）都會建立
GPU texture 與 material，而中文字型是另一個坑。為了「六扇門上的字」
去改整個世界的資源所有權邊界，代價與風險都不成比例。

**也沒有選「只在互動提示裡顯示」**（走到門前才看得到）。
`CONTEXT.md` 那條鏈的第一環是**看見**，而「走到門前」已經是第二環「靠近」了。
在線數如果只在靠近後才出現，Presence 就退回成裝飾。

所以：**常態可見的 DOM overlay ＋ 互動提示重複完整資訊當降級。**

### 重疊怎麼辦 —— Gemini 砍掉了 codex 的第一版

codex 第一版要求「標籤彼此不得重疊到無法辨讀」。**Gemini 指出那是一個佈局引擎**：

> 在正交投影下，這意味著你需要實作一套 2D DOM 節點的碰撞閃避或是動態佈局引擎；
> API 回傳的專案名稱長短不可控，**保證不重疊根本是不可能的任務**。

**codex 承認它對**，並把判準改精確：標籤**固定寬度 ＋ `text-overflow: ellipsis`**
（名稱過長就截字，**不擠開別人**），重疊變成一條**靜態算術檢查**：

```
對任意兩個槽位   |dx| ≥ labelWidth   或   |dy| ≥ labelHeight
```

而且 codex 補了一刀：**不能寫成「中心點的歐氏距離 ≥ 寬度」**，那不足以證明
兩個矩形不相交。

三個附帶要求：用**產品實際使用的**投影純函式算、用**最小支援 viewport**、
標籤尺寸從產品常數來（**測試不得抄一份數字**）。

### 為什麼這條檢查不是恆真的

六扇門的 x 相同，所以 `dx` 恆為 0 —— **這條檢查完全落在 `dy` 上**，
而 `dy` 來自 `sy = (py - pz + tz) × √2/2`。把投影的 `√2/2` 拿掉、
把槽位間距改小、把標籤高度改大，任何一個都會讓它紅。

它**不隨相機移動而改變**（六扇門只差在 z，相機平移對 `dy` 的差值沒有影響）——
所以它是一條乾淨的靜態性質，不是一個會隨環境漂的量測。

## D3：槽位從走廊的矩形推導，不是寫死座標

`FE-W11` 的 D4 只交了矩形，並且**明文拒絕**再帶 `{origin, axis, spacing, capacity}`
給這裡用 —— 理由是「`capacity` 今天沒有讀取者」。

那個「今天」就是現在。所以推導寫在這一邊：

```
zone = ZONES.corridor          // x=-9, halfWidth=2.8, z=3, halfDepth=6
depth = zone.halfDepth × 2 = 12
pitch = depth / SLOT_COUNT
z_i   = (zone.z - zone.halfDepth) + pitch × (i + 0.5)
x     = (zone.x - zone.halfWidth) + doorHalfDepth
```

**容量也是推導的**，不是挑的：

```
SLOT_COUNT = floor(depth / (doorWidth + MIN_GAP))
           = floor(12 / (1.58 + 0.4)) = 6
```

`MIN_GAP = 0.4` 是**視覺常數**：兩扇門之間要看得出來是兩扇，不是一整片木牆。
它是 `FE-W14 VisualPolish` 可以調的東西 —— 調了容量會跟著變，**這是刻意的**。

⚠️ **推導的意思是「改走廊矩形，門要跟著動」** —— 那條判準防的是
「先算出 -2/0/2/4/6/8 然後寫死進去」。寫死的話這一項就跟 `FE-W11` 的分區脫鉤了，
而脫鉤的症狀是「有人把走廊挪了，門留在原地穿牆」。

## D4：溢位 —— 截斷，但不得靜默

codex 第一版提「同一面傳送門牆分頁，提供上一頁／下一頁互動」。
**Gemini 砍掉它**：

> 這代表你必須在 3D 走廊裡**無中生有地創造新的互動物件**（按鈕或箭頭）、
> 增加新的幾何形狀並管理分頁狀態。這完全超出了「依 API 生成門」的範疇。

codex 同意。**折衷是兩邊的交集**：只放六扇（滿足 Gemini 的「不造 3D 分頁 UI」），
而「另有 N 個專案未顯示」由**既有的 DOM 層**講出來（滿足 codex 的「不得靜默截斷」）。

### 排序 —— codex 推翻了自己

它第一版提「`online_count` 遞減」。我追問「會不會造成玩家走到一半門換位置」，
它自己改站對面：

> 它在列表產品裡合理，**在可行走的空間裡不合理**：門的位置形成**空間記憶**，
> 輪詢不應讓玩家正在接近的專案突然換門，甚至掉出前六。
> `online_count` 可以顯示，**但不要決定空間位置**。

所以排序是 **`project_id` 字典序**。

⚠️ **誠實寫下這個做法的缺陷**：新專案的 `project_id` 是 UUID，
它可能插進中間、把既有的門整排往後推，甚至把第六扇擠掉。
**「同一份資料永遠得到同一個排列」成立，「門的位置永遠不動」不成立。**
要後者需要伺服器端的槽位指派，那是 `FE-V01` 真的要「進入房間」時才值得談的東西。

## D5：輪詢的生命週期

契約明文：「`online_count` 只在 REST 回應裡，**不會自己更新** —— 要自行輪詢。」

codex 一開始要我沿用 `FE-R04`（頁籤切到背景時 rAF 會停）的結論。**它自己收回**：

> 輪詢不由 `FE-R04` 自動決定。`FE-R04` 對 rAF／連線生命週期的結論可以作
> 一致性依據，但 **REST polling 是另一個副作用**，必須由 `FE-W12` 明訂。

週期定 **30 秒**。理由：這**不是**即時資料（真正的即時走 WebSocket，
而 `/api/rooms` 明文不會自己更新），30 秒讓「有人進了那個房間」在玩家
走過走廊的時間尺度內反映得出來，同時一小時只打 120 次。
要更快就是 Requirement 變更，不是調一個常數。

**首次載入與輪詢中要分開**：首次載入中不呈現任何門（沒有舊資料可留）；
輪詢中維持目前的門（不得閃成空白）。暫時失敗**保留上一次成功的資料並標示過期** ——
把門全部刪掉會讓走廊在一次網路抖動之後變成空的。

## D6：判準「互動得到」不能寫成算術 —— Gemini 抓到的

`FE-W11` 交下來一條待答問題：「**可走 ≠ 互動得到**：碰撞盒依角色半徑膨脹之後，
玩家可能停在看板 1.5 個單位外，而互動的觸發半徑只有 1.0」。

我原本打算寫成「BFS 求出的可站立格裡至少有一格與物件的距離 < `range`」。
**Gemini 指出那是一把量錯東西的尺**：

> 你只是在驗證「兩份靜態資料的數學關係」。就算你把真正負責互動的
> `Interactable` 註冊機制或 `chooseTarget` 實作全砍了，**這個測試照樣是綠的**。

codex 補了一句更精確的：

> 它不是數學意義上的恆真 —— 常數改壞仍可能紅 —— 但**作為「門真的互動得到」的
> 驗收證據不成立**。

所以判準改成走**真實的路徑**：掛載門 → 角色放到 BFS 求出的可站立格 →
設定朝向 → 跑真實的 `chooseTarget` → 斷言回傳的 id 是那扇門。
靜態的距離檢查最多只能當額外的 layout invariant。

**`TUNING.range` 要重量。** `tuning.ts` 自己寫著那個 `2` 沒有依據、
「真正的數字要等 `FE-W12` 有實際尺寸」。重量的方法就是上面那條判準：
把 `range` 調小到判準變紅為止，紅的那個值就是下界。

## D7：身分不得錯位 —— codex 提的第四條

> 這條不做，畫面仍可能「看起來正常」，玩家卻**從 A 的門進到 B**；
> 是最值得防的第四條。

輪詢更新（回傳 A–F，再回傳「刪掉 B、加入 G」）之後，同一扇門的
**標籤文字**、**React key**、**`Interactable` id** 必須全部來自同一個 `project_id`。
防的是「用陣列 index 當 key」造成的殘留 closure 與錯門。

因為門**不帶 `onInteract`**（見 Non-goals），codex 原本判準裡的
「互動後的目的地或 callback 參數」那一半今天沒有東西可以驗。
兩邊都確認**剩下的一半仍然站得住**：使用者看到的門與 `chooseTarget` 選中的門
沒有錯位，就足以擋住 index-as-key。

## D8：幽靈目標

Gemini 提的：玩家正對著一扇門時，輪詢回傳的資料不含那扇門 →
元件卸載 → registry 是否清乾淨、提示是否消失。

我指出 `SpatialInteraction` 每幀重算，下一幀 `chooseTarget` 就會回 `null`，
所以**它可能本來就是對的**。codex 的回答：

> 「既有機制理論上會處理」不是不測的理由。**`FE-W12` 首次引入了
> 因輪詢而卸載當前互動物件的生命週期**；這個整合邊界以前可能根本不存在。

（`FE-W06-S15` 驗的是「卸載後不得再被選為目標」——
它驗的是**機制**，用的是測試自己掛載與卸載的假物件。
這裡驗的是**這條資料管線**真的會走到那個機制。）

⚠️ codex 附帶一條：**不要求提示與 React unmount 在同一個同步瞬間消失**，
除非既有契約真的如此。判準分成兩件事：卸載後 registry 立即不含該 id；
下一個互動幀之後目標成為 `NO_TARGET`、提示消失。

## D9：內牆的洞跟門對不對得上 —— 不在這一項

`FE-W11` 交下來的第三條：「`S10`（走得到）擋得住『洞太窄或沒有洞』，
擋不住『洞比門寬很多』（看起來牆缺一角）」。

Gemini 主張不做，但**它的事實前提是錯的** —— 它以為走廊隔牆是一個連續的實體，
要挖洞得動態切割 mesh。實際上 `FE-W11` 早就把它拆成兩段，中間留了
`GAP = {center: 3, width: 1.8}`。我把這件事指出來之後，codex 的處置：

> 既然 `FE-W11` 已經留下兩段牆和固定 `GAP`，這只是**尚未被測試固定的
> `FE-W11` invariant**。……不要用 `FE-W12` 的 12 點吸收。

所以：**不列為這一項的判準**。這一項完全不碰那些常數。

## 待答問題

  不保證「門的位置不動」。要後者需要伺服器端的槽位指派 —— 留給 `FE-V01`

  真正的數字是 `FE-W14 VisualPolish` 的事

  正交俯視角下這件事今天不明顯，但 `FE-W13`（40 人同畫面）之後會
- **牆洞算術**（D9）是 `FE-W11` 的債，今天沒有任何機器在檢查它

## D10：規格原文自己被審出七個錯

決定收斂之後，**規格原文再送兩邊審一次** —— 問的不是「決定對不對」，
是「決定在編碼成 Requirement 的時候有沒有走樣」。
**兩邊都投「不同意合併」**，九個發現裡七個是真的。留在這裡是因為
其中三個是這個 repo 已經犯過的錯的**同一類**。

| 發現 | 誰 | 處置 |
|---|---|---|
| `S08`／`S11` **空集合恆真** —— 生成 0 扇門時「每一扇都不相交」自動成立 | Gemini | 補「數目等於容量」 |
| `S07` 同一個病 —— 容量算成 0 或 1 時「相鄰兩個」是空集合 | 我補的 | 補「數目 > 1」 |
| `S16` **恆真** —— 把整套生成與註冊拿掉，「按 E 什麼都沒發生」照樣綠 | codex | 綁在「提示正指著那扇門」＋「登記的動作**不存在**」 |
| `S06` **量詞過強** —— 「每一個槽位的座標都變」會把正確實作判成錯的（只改 x 時 z 本來就不該動） | codex | 改成兩個具體的變換 |
| 「**每一筆回應**對應一扇門」—— 一筆回應是整個陣列，這樣寫走廊永遠只有一扇門 | Gemini | 改成「回應裡的每一筆房間」 |
| `S17` **理由不成立** —— 用陣列索引當 key 不必然造成錯位，正常重繪會一起更新兩邊 | codex | 理由改成「畫面節點與互動登記用了不同的身分或更新時機」 |
| `S20` 與 `S21` **互相矛盾** —— 切背景時請求還在飛、馬上切回來，「立即請求」撞上「最多一個進行中」 | codex | 加「不可見時捨棄進行中那一次的結果」 |
| 「卸載之後不得再更新」**沒有 Scenario** | codex | 補 `S23` |

`S07` 那一條是我自己順著 Gemini 的發現往下找的 —— **同一個病在第三個地方**。

### 兩個沒有採納的

**codex 說 `S13` 的因果寫錯**（「相機固定，角色走遠不會讓門離開畫面」）。
**它的前提錯了**：相機的**朝向與投影**固定，**位置跟著角色**（`world-camera` 的契約）。
不過它指到了一個真的缺陷 —— 規格沒說清楚是哪一種「固定」，
所以補了一句相機的行為。

**Gemini 說「兩塊看板是偷渡進來的」**（「整份規格只跟走廊的門有關」）。
**看板逐字在 `FE-W12` 的 WBS 第一、二個位置**，而且 Gemini 自己在前一輪
選了「看板只加互動註冊」。它這一輪看不到那段脈絡 ——
但這**暴露了規格原文的真實缺陷**：`Purpose` 完全沒有提到看板，
一個沒有參與討論的人讀不出它們為什麼在這裡（`openspec/config.yaml` 明文
要求規格對這種讀者成立）。已補進 `Purpose`。

### 複審又抓到五個 —— 其中一個是我上一輪**修出來的**

| 發現 | 誰 | 處置 |
|---|---|---|
| `S16` 我補的「登記的動作**不存在**，不是空函式」是**實作結構**，不是可觀察行為 | **兩邊獨立指出** | 刪掉。支點改成 `GIVEN`：「提示正指著那扇門」在世界上沒有門時不可能成立 |
| `S15` 空集合 —— 生成壞掉時「對每一扇門」自動成立 | codex | 補「門數等於容量且大於零」 |
| `S12` 空集合 —— 只有一扇門時「其他標籤」是空集合，**擠版需要一個受害者才看得出來** | Gemini | 補「至少兩扇相鄰的門」 |
| `S17` 空集合 ＋ 更嚴重：**兩邊一起綁到同一個錯的 id 也會過** | codex | 補「集合等於新回應」＋「每扇門對應新回應裡的那一筆」 |
| `S20`／`S21` **仍然矛盾** —— 「捨棄結果」不等於「請求結束」，它還在飛 | codex | 改成**中止**（abort），並補 `S24`（晚到的舊回應） |

第一條值得單獨記著：**我上一輪為了修「恆真」而補的那句話，本身是一個新的錯。**
兩個審查者各自獨立指出同一件事 —— 對玩家來說 `undefined` 與 `() => {}`
一模一樣，把它寫進 Scenario 等於用產品義務去綁程式碼長相。

而真正讓 `S16` 不恆真的東西，一直都在它的 `GIVEN` 裡。

### 第三輪：空集合又出現兩次，而且其中一個是「另外那一側」

| 發現 | 誰 | 處置 |

斷言裡有沒有第二個集合？**


## D11：`S13` 的 THEN 寫錯了 —— 實作階段量出來的

原文是「那個標籤**不在 DOM 裡**」。

**那句話會逼出一個 `CONTEXT.md` 明文禁止的做法。** 相機每幀都在追角色，
所以「哪幾扇門在畫面內」是**每幀都在變的高頻資料** ——
要求把節點從樹上移除，等於要求每幀讓 React 重繪那一層，
而 `CONTEXT.md` 的原文是「違反這條不會有錯誤訊息，只會變慢」。

Requirement 本體給的**理由**一直是對的：

> 它仍然留在 DOM 與無障礙樹裡，螢幕閱讀器會念出一個看不到的東西。

`visibility: hidden` **完全滿足那個理由** —— 它同時把元素移出畫面與無障礙樹
（跟 `opacity: 0` 不同）。而「絕對定位的元素撐開版面」那一半由容器的
`overflow: hidden` 解掉。

所以改的是 **THEN 的措辭**，不是判準的強度：
「不呈現，也不在無障礙樹裡」。

**這是這個 change 第三次規格自己被實作測出錯**
（前兩次在審查階段：`S16` 的恆真、`S20`／`S21` 的矛盾）。
同一個形狀：**Requirement 的理由對，Scenario 的 THEN 寫過頭**，
把一個實作手段寫進了產品義務。


## D12：`S11` 的「數目等於容量」在最小畫面上是假的 —— 截圖抓到的

走廊的深度是 12，而相機的垂直可見範圍**也是 12**（`viewHeight`）。
所以站在走廊裡，最北或最南那一扇門本來就在畫面外 ——
在最小支援尺寸（320×480）量出來是 **5/6**。

那不是缺陷，是**空間本來的樣子**。而 `S11` 寫的是「標籤的數目等於容量」，
於是判準在正確的實作上會紅。

改成兩半：

- **看得見的至少兩個** —— 擋空集合（跟 `S07` 同一個理由）
- **相鄰槽位投影後的縱向距離 ≥ 標籤高度** —— 這一條**與畫面上實際出現幾個無關**，
  它直接問「間距夠不夠」，所以把標籤改高、或把槽位排密，它都會紅

## D13：人工截圖抓到兩個測試全綠的錯

**這一項到這裡為止，單元測試 442 條全綠、九輪突變全紅。**
然後我開瀏覽器截了四張圖，兩個問題立刻看得見：

**① 走廊在畫面外的時候，六個標籤仍然貼在畫面左緣，各被切掉一半。**

規格 `S13` 的理由那一段講的就是這件事 ——
而我第一版的實作判的是「**標籤的矩形**有沒有完全跑出畫面」，
規格寫的是「**門的投影**落在畫面之外」。**兩個不是同一件事。**
判準跟著實作寫，所以它是綠的。

修法：整個矩形都要在畫面裡才顯示。

**② 每一個標籤都被截字。**

`進入「星際導航」（3 人在線）` 在 168px 裡變成 `導航」（3 ...`。
固定寬度的意義是「不讓後端決定版面」，**不是「把每個名字都截掉」**。

修法：常態標籤與互動提示分成兩份字（`doorTag` 與 `doorLabel`），
**兩份都從同一組欄位算**。標籤 `星際導航 · 3 人`，提示維持完整句子。

⚠️ 這兩個都是**只有截圖看得到**的。`FE-W10` 目視抓到兩個、`FE-W11` 抓到一個、
這裡兩個 —— **人工瀏覽器檢查不是形式，它是這個 repo 目前唯一驗得到「畫面對不對」的東西**。
