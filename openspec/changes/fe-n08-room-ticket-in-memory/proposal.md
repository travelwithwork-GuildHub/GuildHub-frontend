# fe-n08-room-ticket-in-memory：房間票改以記憶體為主，storage 被擋也進得了房

## 為什麼現在做

產品負責人 2026-09-22 實測 demo：重新部署後，**一整隊在正常瀏覽器視窗都進不了任何專案房間** ——
輸對密碼、按「進入」，卻被判成「存不了通行證」留在大廳，**只有無痕視窗能進**。原話：
「硬重新整理 Cmd+Shift+R 還是不行／我用無痕就可以／可是這樣我主要使用的瀏覽器就沒辦法了／
之前使用過的人都會有問題／這個問題要解決！！！」

根因（實測＋邏輯鎖定）：`POST /api/projects/{id}/enter` 需要有效 session cookie（沒登入一律 401，實測過）。
所以會看到「拿不到通行證」的人**一定已經登入、cookie 沒被擋、`/enter` 也成功拿到了票**。
剩下唯一會失敗的是規格當初定的那句「把票寫進 `sessionStorage`、讀回嚴格一致才算成功」——
這些使用者的瀏覽器（隱私擴充套件／站台儲存設定／部分無痕）**擋掉了這個網域的 DOM storage**，
而 cookie 沒被擋。於是 `/enter` 過、票拿到了，卻卡在「存不進 storage」這一關。
無痕沒有那個擴充 → storage 通 → 就好（這正是「無痕能進、主力瀏覽器不行」的成因）。

**不做會怎樣**：整個團隊在自己的主力瀏覽器都無法測試、無法 demo；每一個「之前用過這個站」的人都中這個雷。
這不是密碼錯、不是後端、不是快取 —— 是前端把「票的持久化」錯當成「進房的必要條件」。

## 做什麼

把房間票的**權威來源從 `sessionStorage` 改成模組級記憶體 `Map`**；`sessionStorage` 降級為
「重新整理後撿回票」的 best-effort 持久層。

- `holdRoomToken`：寫記憶體（權威、一定成功）＋ best-effort 寫 `sessionStorage`（寫不進去不拋、不影響持有）。
- `heldRoomToken`：記憶體知道這個鍵就以它為準（持有過 → 票；丟過 → 墓碑 `null`，不回頭問 storage）；
  記憶體沒見過（多半是重整後的新一場）→ 從 `sessionStorage` 撿回，撿到就放進記憶體當這一場的權威。
- `dropRoomToken`：記憶體放**墓碑**（`null`、一定成功）＋ best-effort 清 storage；一律回 `dropped`。

效果：**storage 被擋也照樣進得了這一場的房間**（修掉「只有無痕能進」）；只有「重新整理頁面」後才靠 storage
撿票，撿不回就回大廳、走到門前再拿一次（遠優於整隊進不去）。丟票由記憶體墓碑保證成功，
storage 刪不掉也不會拿舊票撞握手。

與 codex（gpt-5.6）討論一致（見 `design.md`）：`world-scenes`〈票由前端持有〉用 **MODIFIED**（標題未變、只改持有模型）；
`room-entry-gate`〈成功先存票再進房；**票存不進去就不算成功**；有票的人不再被問〉的標題那句是一個**明確、且已被反轉**的產品承諾，
MUST 用 **REMOVED + ADDED** 改名，不能用文字詮釋把「存不進去就失敗」硬讀成別的意思迴避掉。

## Non-goals（不做什麼）

- **不改後端、不改 `/enter` 契約、不改握手驗票**：票的內容、TTL、綁定都不動。這是純前端持有策略的修正。
- **不把票變成安全邊界**：記憶體同源 XSS 讀得到、複製分頁帶走副本 —— 跟原本 storage 一樣不是安全邊界，
  安全仍靠 CSP／輸出安全（`FE-T06`）／後端 8 小時 TTL／分頁資格（`multi-tab`）。
- **不追求跨分頁共享票**：storage 被擋時，另一個分頁／新視窗沒有這份記憶體 `Map`，接不了票 ——
  這是設計的自然限制，明寫進規格，不在這個 change 解。
- **不清理墓碑累積**：票隨造訪過的 profile/project 累積 tombstone，量級對 demo 無感；生命週期清理記為之後。
- **不動 `localStorage`、不把票放進網址**：原本的禁令原封保留。
