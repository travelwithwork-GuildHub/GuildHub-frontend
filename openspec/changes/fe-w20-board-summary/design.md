# Design —— fe-w20-board-summary

決策跟 codex（gpt-5.6）與 gemini（3.1 Pro）各問一次、互審。**D1／D2／D3 兩邊一致**，D4／D5 有分歧，取捨記在下面。

## D1 — 常駐訂閱的生命週期：獨立的 `useBoardSummary`（兩模型一致）

看板摘要要在**面板關著**的時候也顯示，所以不能搭面板的 `useListPage`（那個只在面板掛載時活著）。

**決定**：新 hook `useBoardSummary(kind)`，抓 page 0、每 30 秒輪詢、分頁隱藏就停、回到可見立即重取、單一在飛的 `AbortController`、
失敗保留舊的（stale）—— 完全照 `useRooms` 那套（走廊門也是常駐世界物件的資料）。**跟面板各自獨立**，不共享 fetch／cache。

兩模型都選 A、都反對把分頁狀態抬進共享 store：那是 demo 不需要的耦合，`useRooms` 是這個 repo 已經驗過的常駐輪詢樣板。
**併發**：輪詢寫 seats／doors 那種「舊回應晚到蓋掉新的」的洞在這裡一樣要防（單飛 controller ＋離場 abort）。

## D2 — 一致性判準：最終一致（兩模型一致）

看板畫 page 0 的前 4 筆、面板畫整個 page 0。兩邊獨立輪詢 → 會有短暫不一致（看板 20 秒前輪詢的、面板剛開）。

**決定（可測判準）**：**兩邊都 ready、且對應同一個底層 page 0 時**，看板顯示的標題 SHALL 恰好是面板 page 0 items 的前
`min(4, n)` 筆、同順序。短暫不一致可接受，兩邊在一個輪詢週期（≤30 秒）內收斂。**不做共享 store**（強一致是過度工程）。

## D3 — 狀態呈現與 `FE-X04` 語彙重用（兩模型一致）

看板是 mesh 面上的幾張卡、不是面板，塞不下也不該塞 panel 尺寸的 `<EmptyState>`。

- **重用「判斷」不重用「版面」**：沿用 `paging.edgeState()`（first-empty／exhausted／error）與 `failureKind()` 的分類、
  沿用 `FE-X04` 的**文案字串**（空的用「這裡還沒有東西。」），但**版面是看板原生的**緊湊卡（不 mount `<EmptyState>`）。
- **載入中＝骨架卡**（兩模型一致選骨架，不選文字、不選空白）：骨架填住既有卡槽，遠遠看就懂「內容要出現在這裡」，
  且**不說謊** —— 先畫「空位」會是謊（跟 `FE-J13-S01`／座位同一條原則）。
- **讀不到＝環境化錯誤**：`role="status"`、**沒有 retry 按鈕**（兩模型一致）。看板是環境資訊，重試留給按 E 開出來的面板。
  這是對 `FE-X04` 面板行為的**刻意降級**：面板裡 `load-failed` 是 `role="alert"`＋retry，看板一律 `role="status"`＋無 retry
  （permission-blocked 本來就是 status／no-retry，不變）。曾有資料就保留 stale，不閃成空白。

## D4 — 幾筆、哪個欄位：N = 4（分歧，取 gemini）

- codex 選 N=3（遠距離較好讀），gemini 選 **N=4**（對齊看板 mesh 上既有的 4 個卡槽、視覺和諧、不必改幾何）。
- **取 N=4**：mesh 已經畫了 4 張空白卡，摘要就填那 4 槽 —— 讓資料驅動的內容對上既有幾何，比另立一個 3 的數字少一份漂移。
  **資料驅動**：page 0 有 `n` 筆就填 `min(4, n)` 張、其餘卡維持空槽（不補假卡）。
- **欄位**（兩模型一致）：專案看板＝案件標題、人才看板＝人才 `display_name`，**單行、超出截斷加省略號**（固定寬、不隨字長變）。

## D5 — 從出生點的可辨識性與擺放：釘在看板面（分歧，取 gemini 的擺放＋codex 的判準底線）

- codex 要「文字從 spawn 就讀得清」（放大／浮在看板上方）；gemini 要「釘在看板面（`DoorLabels` 式），從 spawn 看得出**卡的形狀／顏色**
  就夠了（有字的卡 vs 骨架 vs 空 vs 錯），走近才讀得到標題」。
- **取 gemini 的擺放**：巨大浮字破壞臨場感；**但把 codex 的核心要求寫成判準的底線** —— 規格的「從房間另一端看得出」是綁在
  **狀態訊號**（填了字的卡／骨架／空／錯，四者從 spawn 分得出來），不是綁在「讀得到標題」。標題走近讀得清即可。
  這樣同時滿足 WBS 的兩件事：可辨識摘要（標題，近距離）＋三態從遠處看得出（狀態訊號）。
- **投影**：用工位錨點／門標籤同一份 `screenPixelFor`，DOM 在 Canvas 外、projector（`useFrame`）在 Canvas 內每幀寫
  `translate3d`＋visibility，畫面外整塊移出無障礙樹 —— 跟 `SeatAnchorProjector` 同一條路（NaN 前置檢查照抄）。
- **看板面錨點的 y**（`fe-b01` `D5` 的頭部裁切懸案）：看板高 ~2.3、在 z=-6.5，出生點 z=-1。錨點取**卡槽的世界 y**
  （看板面上四張卡的中心），實作時量出實際數字寫進常數；出生點視角有輕微遮擋可接受（要分辨的是四態的粗略形狀／顏色，不是讀字）。

## 兩模型都點名的最大風險

- codex：投影 DOM 在 spawn 視角被角色頭部／透視遮擋 → 「可讀」只存在設計稿。
- gemini：projector 落後相機一幀 → 卡片在看板面上「游移」，戳破「這是實體物件」的錯覺。

→ 同一件事：**overlay 必須跟著相機釘死、且狀態訊號在實際遊玩鏡頭（不是設計稿）分得出來**。
緩解：沿用已驗過的 `SeatAnchorProjector`／`screenPixelFor`（不自寫投影）；真瀏覽器 e2e 驗「移動時 overlay 保持釘在看板面」與
「從 spawn 分得出有資料／空／讀不到／載入中」。

## ADR

新 ADR `0015`：`world-board-summary` 是**第四個** render loop → DOM 的消費者（門標籤、工位錨點、名字牌之後）。
依 ADR 0010 的「重新考慮」條款：投影仍用同一份 `screenPixelFor`、**不抽通用元件**（考慮過，四個消費者的錨點來源／內容型別各異，
共用的只有那一行投影數學，已經共用了）。0015 記這條邊界與「為什麼看板摘要不共用面板資料」（D1）。
