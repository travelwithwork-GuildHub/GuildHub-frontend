## 量測

三件事都是這一刀開始之前實際跑過的，不是推論。**它們決定了整份規格的形狀。**

### M1 —— 缺設定的 production 建置：綠燈、上線白畫面

```
NEXT_PUBLIC_APP_ENV 與 NEXT_PUBLIC_GUILDHUB_WS 都不設 → next build
  → 建置成功，零警告
  → next start，GET /            → 307 → /world
  → GET /world                    → 200
  → 畫面上只剩下「GuildHub」，3D 世界從來沒有出現
```

原因鏈（讀出來的，不是猜的）：`wsUrl()` 第一次被呼叫是在
`RemoteWorld` 的 `useEffect` 裡（`client.connect()` → `connectionUrl()` → `wsUrl()`）。
`resolve()` 在 `appEnv() !== 'local'` 且變數缺席時拋 `ConfigError`。
effect 拋出的錯沒有邊界接（`FE-X01` 的重試邊界包的是路由層），整棵樹倒掉。

**`fe-o09-env` 的守衛是對的，錯的是時機。** 那些檢查在執行期跑，
而部署設定的錯誤在**建置期**就已經完全確定了 —— 它讀的是同一份
`process.env`，只是早了幾分鐘，而那幾分鐘的差別是「CI 紅」與「訪客看到白畫面」。

### M2 —— 有位址但連不上：世界正常，畫面零提示

```
NEXT_PUBLIC_APP_ENV=production
NEXT_PUBLIC_GUILDHUB_WS=wss://<一個不存在的位址>/ws   → next build → next start

  /world  → 200，世界出現，方向鍵走得動（x 從 0 走到 6.4 撞到世界邊界）
  console → 一行 WebSocket 連線失敗
  畫面    → **沒有任何說明**
```

畫面上那個 `role="alert"` 是 Next 注入的**空的** route announcer，不是錯誤呈現。

**沒有重連。** `src/realtime/` 底下沒有任何 `setTimeout`／`backoff`／`retry`
（那是 `FE-R12`，W5）。所以行為是「一次失敗，之後永遠安靜」——
對部署反而是好事（不會有訪客的瀏覽器無限重試），但它讓**空世界變成穩定狀態**，
而訪客分不出那是「本來就沒人」還是「壞了」。

### M3 —— 前端今天零 REST

```
grep -rn "api/operations|api/transport" src/ --（排除 src/api/ 本身）→ 無
```

`src/api/operations.ts` 的 16 個操作**沒有任何元件 import**。
畫面上唯一會動的東西全部走 WebSocket。這條決定了 D1。

### M4 —— `next.config.ts` 什麼時候被載入（用探針量的）

在 `next.config.ts` 最上面放一行印出 `NODE_ENV` 與 `argv` 的探針：

```
next dev    → NODE_ENV=development   載入 1 次
next build  → NODE_ENV=production    載入 2 次（argv=build，以及一次 argv 空的子行程）
```

這回答了「在 config 裡呼叫設定函式會不會把本機開發一起擋死」：**不會**。
`appEnv()` 已經用 `NODE_ENV` 當守門員 —— dev 時它回 `local`，
`resolve()` 於是回本機預設值，不拋錯。

**所以不需要在 config 裡判斷建置階段（phase）。**
這正好是 D3「呼叫同一份函式」的價值：那個判斷已經在 `env.ts` 裡了，
在 config 再寫一次 phase 判斷，就是第二份會漂的邏輯。

載入兩次是無害的（驗證只讀不寫），但寫下來免得有人看到兩次輸出以為是 bug。

## 決策

### D1 —— 不用 Next.js 寫測試後端

原本的提議是「用 Next.js 先做一個測試的後端，之後再串接正式的」。
拆成兩半之後兩半都不成立：

**REST 那半：做了不會有任何差別。** 由 M3 —— 沒有元件呼叫它。
唯一的反例是「同時改前端，把 presence／position 改成 REST 輪詢」，
但那不是「先做測試後端」，那是**重做即時協定**，而且會製造兩條暫時的資料路徑。

**WS 那半：Vercel 是錯的形狀。** Vercel 官方文件：

> WebSocket connections on Vercel are pinned to a specific Function instance
> for their duration. Because clients may connect to different instances,
> Redis is used to share room events and presence across these instances.

不接 Redis → 兩個訪客可能落在不同 instance → **兩個互不相見的房間**。
join／leave／chat／snapshot 各自都正確，全域是錯的，而且是**間歇性的**。
對一個要給別人看的部署，這是最糟的失敗形態：看的人分不出是網路、是 bug、
還是架構限制，只會得到「你們的東西是壞的」。
接了 Redis 也只解決跨實例共享，**不解決 10 Hz 房間 tick 的生命週期**。

**而且會製造協定漂移。** 真實來源是後端的 `protocol.py`（`CONTEXT.md` 明訂）。
用 TypeScript 再實作一次 10 Hz 廣播、「沒有人移動就不送 `pos`」、
`presence` 的 join／leave 合併、整數座標的靜默丟棄 —— 等於同一份協定有兩個實作，
而**只有其中一個是真實來源**。

**要真的多人的路徑**：把已經存在的 FastAPI 部署到常駐容器。
它的 `PresenceStore._players` 是行程記憶體 dict，常駐容器正好是那個形狀，
一行程式都不用改。**那不在這個 change 裡**（需要帳號與帳單決策）。

> 諮詢紀錄：這一條分別問過 codex 的 gpt-5.6-terra 與 Antigravity CLI 的
> Gemini 3.1 Pro，兩邊獨立得到同一個結論（不要用 Next.js 寫，部署現有的
> FastAPI）。Gemini 另外主張 Vercel function 的執行時間上限會擋死 10 Hz loop，
> **那條理由沒有採用** —— Vercel 目前所有方案的上限是 300 秒，
> 它引的 10／60 秒是舊的。結論不受影響，但錯的理由不寫進規格。

### D2 —— 「沒有即時後端」要明確宣告，不能靠「沒設位址」推斷

最省事的做法是「`NEXT_PUBLIC_GUILDHUB_WS` 沒設 = 單人預覽」。**不採用。**

那會直接推翻 `fe-o09-env` 建立的那條規則：**缺席不得安靜退回**。
一個忘了設 WS 位址的正式部署會**安靜地變成單人模式** —— 而症狀是
「怎麼都看不到別人」，不是「設定漏了」。那正是 `env.ts` 檔頭花了二十行在防的東西。

所以用一個明確的值：`NEXT_PUBLIC_REALTIME_ADAPTER=none`。
**要單人預覽必須自己寫出來。**

順帶補掉一個既有的不對稱：REST 已經有 `NEXT_PUBLIC_DATA_ADAPTER`
（`guildhub` / `internal`），WS 那條路卻是直接讀位址。
兩條路現在有同一個形狀 —— 而這也是之後真的接上後端時要動的唯一一個地方。

**刻意不重用 `NEXT_PUBLIC_DATA_ADAPTER`。** 兩個軸會分開移動：
之後 `FE-O03` 的本地後端做好時，REST 走 `internal` 而 WS 仍然可能是 `none`
（Route Handlers 給不了 WebSocket）。合成一個變數的那天，
其中一邊會被迫說謊。

### D3 —— 建置時驗證迭代**一份清單**，而不是逐一列舉變數

`next.config.ts` 在建置時於 Node 執行（M4），那時 `process.env.NEXT_PUBLIC_*`
已經齊全 —— Next 就是在那之後才把它們靜態替換進 bundle 的。
在那裡驗證，讓 `ConfigError` 直接往外拋，`next build` 就會紅。

**第一版寫的是「MUST NOT 在 config 裡重寫一份檢查」。那條規定測不到。**
複審時被指出：任何黑箱的建置測試，對「呼叫了同一份函式」與
「手寫了一份剛好等價的檢查」都會給出綠燈。**一條驗不到的規定就是一條裝飾。**

改成一個結構上就成立的形狀：設定模組匯出一份清單，
每個項目有變數名稱、解析函式、以及「部署建置時要不要驗」。
建置時的驗證**迭代那份清單**。

於是：

- 沒有第二份清單可以漂 —— 想「另寫一份」的人得先造一份清單出來，
  而那件事在 review 上看得見。
- **測試也由那份清單驅動**（`FE-O14-S06`）：對每個必驗項目逐一移除它的變數，
  斷言驗證失敗。新增一個項目時這條**自動涵蓋它**；
  寫死項目名稱的測試做不到這件事，那正是規格裡明文禁止寫死的原因。

**第一版還有一整條「涵蓋率守衛」（掃 `env.ts` 找出所有 `process.env` 讀取點，
比對一份豁免清單）。砍掉了。** 兩位複審都反對，理由一致而且說服了我：
那種掃描靠字串比對，helper、alias、一次重構就騙得過；
而它紅起來的時候，下一個人最省力的動作是**把新變數塞進豁免清單交差** ——
於是它變成一個從來沒有抓到過任何東西的儀式。
清單本身就是那份涵蓋率，不需要再有一個東西去掃它。

**已知缺口，明寫出來**：`restBase()` 在清單裡標為「建置時不驗」，
理由是今天沒有任何元件呼叫它（M3）。把它列成必填等於要求一個什麼都不做的變數。
之後有人接上 REST 時，要把那個標記翻過來 —— 而那件事沒有機器擋著，
靠的是清單裡那行理由被讀到。

### D4 —— 「刻意沒有後端」與「後端連不上」不得共用同一個呈現

兩者在畫面上都是「看不到別人」，但**可安全處置的方式相反**：

| | 使用者該做什麼 | 我們該做什麼 |
|---|---|---|
| `adapter = none` | 沒事，這是預期的 | 說明這是單人預覽 |
| 有位址但連不上 | 稍後再試／回報 | 重連（`FE-R12`） |

共用一個「看不到別人」的提示，等於在真的壞掉的那天告訴使用者「一切正常」。
所以規格把它們寫成兩條 Requirement，而且明文禁止單人預覽的提示出現重試操作
—— 理由跟 `FE-W01-S06` 的 WebGL 提示一樣：**永遠不會成功的按鈕比沒有按鈕更糟**。

「有位址但連不上」的呈現**不在這一刀**（`FE-R12`，W5）。
這一刀只保證它不會被單人預覽的提示蓋掉。

## 驗證方式

這個 repo 沒有瀏覽器驗證規範（`FE-O11` 定的是分工，不是逐項的驗證法），
所以逐條寫出來：

- **V1 建置閘門**：對一個 `next build` 真的跑，而不是只呼叫那個驗證函式。
  「函式會拋錯」證明不了「建置會失敗」—— 中間隔著 `next.config.ts` 有沒有真的被載入、
  拋出的錯有沒有被 Next 吞掉。**用 exit code 判定。**
  每一次建置用**獨立的輸出目錄與乾淨的環境變數** ——
  共用 `.next` 的話，成功案例可能是上一次的產物，而那會給出假綠。
- **V2 突變測試（驗收條件）**：把 `next.config.ts` 裡那一行驗證拿掉，
  V1 必須變綠（也就是測試變紅）。這是「拿掉防禦要變紅」那條規則在這裡的形態。
- **V3 清單驅動**：`FE-O14-S06` 的測試從匯出的清單產生案例，
  不得寫死變數名稱。**驗收方式是加一個假項目進清單，案例數要跟著增加。**
- **V4 單人預覽不連線**：斷言 socket 工廠的**呼叫次數**（`none` → 0、`guildhub` → 1）。
  斷言「畫面上沒有別人」是恆真的 —— 沒有後端時本來就沒有別人。
- **V5 連線失敗之後**：先斷言工廠**被呼叫過**，再從替身觸發 `close`
  （不觸發 `open`），然後斷言單人預覽的說明不存在。
  **少了第一步，一個沒走到連線路徑的測試也會綠。**

**測試連到什麼**：不適用 —— 這個 change 的測試不連任何外部服務。
`next build` 在本機跑，不需要網路；單人預覽的路徑刻意就是「不建立連線」。

## 這把尺量不到什麼

誠實寫下來，免得之後有人把它當成比實際更強的保證：

- **證明不了 Vercel 上真的會紅。** V1 驗的是本機的 `next build` exit code。
  Vercel 用同一個指令，但它的環境變數注入是主控台的設定 ——
  **那份設定在 repo 裡沒有任何對應物**，程式碼證明不了它。
- **證明不了訪客看得懂那段提示。** 只證明它在 DOM 裡、講的是單人預覽。
- **不涵蓋 REST 的設定**（見 D3 的缺口）。`restBase()` 在清單裡是**明確不驗**的，
  而「之後有人接上 REST 時要把它翻過來」沒有任何機器守著。
- **證明不了建置時用的是執行期同一份函式。** D3 把它變成結構上比較難違反，
  但沒有變成測得到 —— 那條靠 review 看，不靠閘門。誠實記在這裡，
  免得有人把 D3 當成比實際更強的保證。
