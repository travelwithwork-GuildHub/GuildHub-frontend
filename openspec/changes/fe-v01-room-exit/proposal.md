# fe-v01-room-exit：走出房間就回大廳

## 為什麼現在做

產品負責人 2026-09-21 實測 demo：進了專案房間之後**離開房間的唯一方法是點畫面右上角一顆 DOM 按鈕「回到 Guild Hall」**，
而他根本沒發現那顆按鈕，原話：「這是個 3D 世界，我怎麼可能還去點右上角？**我離開門就應該到下一個場景了，不應該還去點按鈕。**」

**不做會怎樣**：使用者進房間後**感覺回不去**（demo 現場的直接反應就是「卡住了」）。這不是 bug —— 過場邏輯是對的、按鈕也能用 ——
是**設計缺口**：在一個可走動的 3D 世界裡，把「離開場景」這個空間動作綁在一顆網頁按鈕上，正是使用者一再反映的「還在操作網頁、沒有 3D 體驗」。
房間南牆本來就有一個門洞（目前純造型、無互動），卻不能從那裡走出去 —— 空間語彙已經擺在那裡，只差把它接上。

## 做什麼

把「離開房間」變成**空間動作**，三條路走同一套既有過場、都不丟票：

1. **穿門即走（主要）**：往南穿過門洞、進門廊（`z ≥ 10.5` 且 `|x| ≤ 0.75`）→ 自動回大廳，不用按鍵。
2. **門前按 E（對稱、可發現）**：走到門前顯示提示「回到大廳」，按 E 回大廳。
3. **DOM 按鈕（無障礙後備）**：保留右上角「回到 Guild Hall」，給純鍵盤／讀屏／卡住的人。

與 codex（gpt-5.6）、gemini（3.1 Pro）討論一致（見 `design.md`）：穿門即走最符合使用者心智、門檻放門洞以南不誤觸、進按 E／出用走的不對稱自然且剛好防傳送迴圈、DOM 按鈕保留但降級。

## Non-goals（不做什麼）

- **不改回大廳的過場狀態機、連線、票、網址處置**：三條路都呼叫既有的 `returnToHall()`，行為完全一樣。這個 change 只多兩個**觸發點**。
- **不改進房間的互動**：進房仍是走到門前按 E（`FE-V01-S10`）。進出的不對稱是刻意的。
- **不做房間之間直接互通**：出口只回大廳。
- **不在這裡改 DOM 按鈕的視覺**：它「降級成小圖示」跟著 `FE-X17`（header 群島化）做；這裡只確認它保留、可用、有正確的無障礙標籤。
- **不動門洞的碰撞或造型**：門洞仍無碰撞、可穿過；不新增第二份座標（觸發門檻的常數放進既有的 `projectRoomLayout.ts`，唯一那份房間座標）。
- **不做「減少 3D 導航」的無障礙偏好模式**：模型提過，但超出 demo 範圍，記為之後。
