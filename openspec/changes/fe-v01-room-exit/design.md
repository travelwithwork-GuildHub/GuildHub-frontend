# design：走出房間

## 兩個模型的結論（codex gpt-5.6 ＋ gemini 3.1 Pro，2026-09-21）

問題：3D 世界裡離開房間該怎麼做？現況只有右上角 DOM 按鈕，使用者說「離開門就該到下一個場景」。

**兩邊高度一致：**

| 議題 | 結論 |
|---|---|
| 主要互動 | **穿門即走（傳送門式）**：靠近門顯示提示、真的穿過門洞就自動過場。最符合「離開門就到下一個場景」的心智。 |
| 是否保留 E | 保留成**可發現的對稱選項**（門前提示＋按 E），不強制。習慣按 E 的人有對稱操作、也讓出口看得出是出口。 |
| 觸發門檻 | `z ≥ 10.5` 且 `|x| ≤ 0.75`（門在 9.75、出生點 6.75、門洞淨寬 1.8→半寬 0.9）。要刻意往南穿過門洞才觸發。 |
| 進出不對稱 | 自然：進房是「決策」（多扇門、按 E 確認），出房是「釋放」（單一出口、走出去意圖已明確）。 |
| DOM 按鈕 | **保留**（無障礙／鍵盤／讀屏／卡住的逃生門），但**視覺降級**（併進 FE-X17 header 群島化）。不可拿掉。 |
| 提示文字 | 短、指目的地：「回到大廳」。 |

## D1：觸發門檻的數字怎麼定

- 出生點 `z = 6.75`、內側南牆／門 `z = 9.75`、門廊 `z ∈ (9.75, 12)`、外層邊界 `z = 12`。
- 門檻 `z ≥ 10.5`：已經穿過門（9.75）進門廊約 0.75；離出生點 3.75，必須**明確往南穿門**。
- `|x| ≤ 0.75`：門洞淨寬 1.8（`x ∈ [-0.9, 0.9]`），要求 `≤ 0.75` 代表人**在門洞裡**穿過去，不是貼著南牆邊緣擦過。
- 常數放進 `projectRoomLayout.ts`（`ENTRY` 旁邊），跟門座標同一份推導出來 —— 門移了門檻跟著動，不會漂。

## D2：一次性觸發，靠既有的過場鎖

- 穿門觸發器是 Canvas 內一個 `useFrame` 元件（不渲染東西），每幀讀 `LocalPlayer` 寫的 `poseRef`。
- 進到觸發區 → 呼叫 `returnToHall()` → 立一個 `fired` ref，之後那一幀起不再觸發。
- `returnToHall()` 使 `transition ≠ null` → 既有的 `SceneTransitionOverlay` 用 `holdInputLock('scene-transition')` **當幀鎖住移動**（layout effect，畫下一幀前就鎖）。角色不會在門廊繼續往南、不會重複觸發。
- 回大廳後**房間子樹整棵卸載**（`WorldCanvas` 以 scene 當 key），觸發器隨之消失 —— `fired` 也跟著沒了，下次進房是新實例。

## D3：為什麼不會傳送迴圈

模型都提醒的坑：對稱傳送門（走進去 A→B、B 的落點又在 A 的觸發區）會在按著前進鍵時無限來回。
**我們的不對稱剛好免疫**：回大廳後就算按著前進鍵，也不會自動再進房 —— **進房一律要按 E**。所以大廳出生點落在哪裡都不會被「吸回」房間。
（大廳出生點 `z = -1`，本來就不在任何專案門的互動範圍；就算在，進房要 E 也不會自動觸發。）

## D4：E 的互動怎麼接

- 在 `SceneObjects` 的 `room` 分支註冊一個 `Interactable(id='room-exit', x=ENTRY.doorX, z=ENTRY.wallZ, label='回到大廳', onInteract=returnToHall)` ——
  跟大廳的 `ProjectDoors` 用**同一個機制**（靠近＋面對顯示提示、按 E 觸發）。`onInteract` 用 `useCallback` 釘住 `returnToHall`。
- 提示文字就是 label「回到大廳」（跟大廳門的「進入 ○○」對稱）。

## 驗證

- **jsdom**：餵位置序列給穿門觸發器 → 斷言 `returnToHall` 在跨過門檻那一刻恰好呼叫一次、正常走動不呼叫；`Interactable` 註冊在 `room` 場景、按 E → `returnToHall`。
- **e2e（真瀏覽器，打本機 dev server ＋ 偽造即時層/REST，不連共用位址）**：進房→往南走穿門→量到回大廳（socket 變 `scene=lobby`、只建一條）、票還在、網址 `/world`。沿用 `scene-switch.mjs` 的 walker／假後端。
- **不適用**：不連任何外部服務。
