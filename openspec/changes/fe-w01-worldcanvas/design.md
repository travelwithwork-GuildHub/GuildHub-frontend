## Context

動機見 `proposal.md`，需求見 `specs/`。這裡只寫形塑做法的既有條件：

1. **那道縫已經在了。** `FE-X01` 交出的 `WorldBoundary.tsx` 是
   `'use client'` ＋ `next/dynamic({ ssr: false })` ＋ 一個 `catchError` 邊界。
   本次**只改它動態 import 指向誰** —— 殼的結構、邊界、fallback 與重試邏輯
   都不動。（換掉被載入的檔案就必然要改那一行 import，
   所以「完全不動這個檔案」是做不到的，不要把驗收寫成那樣。）
2. **jsdom 沒有 WebGL。** 這份規格有一半以上在 component test 裡驗不到。
3. **E2E 還沒裁決**（`FE-O11`），所以渲染面的自動化不能在這裡開先例。

## Goals / Non-Goals

**Goals:**

- 讓後面五個 W1 的 3D 項目有一個已經在跑的 render loop 可以掛
- 讓「這台機器跑不跑得動」第一次有答案，而且答錯時不是白畫面
- 讓每一條 Scenario 都指名靠什麼證明 —— **沒有一條留白**

**Non-Goals（設計層面）:**

- 不建立 3D 元件的組織慣例（`FE-W09`／`FE-W10` 會定）
- 不決定 render loop 的更新策略（on-demand vs always）—— `FE-W13` 的效能預算
  出來之前那是猜的，列在待答問題

## Decisions

### D1：WebGL2 偵測在**掛 Canvas 之前**，用一個純函式

不是等 `<Canvas>` 拋錯再接。理由：R3F 建立 context 失敗時的行為依版本而異，
而且錯誤會穿過 `FE-X01` 的重試邊界 —— 那個邊界會給出一顆**重試按鈕**，
但 WebGL2 不可用時重試永遠不會成功。**規格 S06 明文禁止那顆按鈕。**

所以先判斷，判斷不過就根本不掛 Canvas。

副作用：偵測本身是一個 `canvas.getContext('webgl2')` 呼叫，
在 jsdom 裡可以被 mock —— 這讓 S06／S07 變成**可以用 component test 證明的**，
而不是只能靠瀏覽器。

### D2：`FE-W10` 會移除的東西放在一個叫得出名字的地方

臨時的平面與方塊放在單一檔案，命名與註解直接寫明它是除錯場景、
由 `FE-W10` 移除。**不要叫它 `Floor`** —— 那是 `FE-W10` 的名字，
用了之後沒有人分得出「臨時的」跟「正式的」。

### D3：載入中的呈現用 R3F 的 `<Suspense>` ＋ **DOM** fallback

規格 S04 明寫「該等待狀態 SHALL 是 DOM 元素，不是 3D 物件」。
理由在規格裡：WebGL 還沒起來的時候畫不出 3D 的等待畫面。

實作上是把 `<Canvas>` 與一個 DOM 疊層放在同一個容器，
疊層在 3D 內容 ready 之前顯示。

### D4：DPR 上限 2

規格把它寫進 Requirement 而不是留給實作，因為它是**可觀察的**：
在 3x DPR 的螢幕上，不設限會用九倍的像素去畫同一個畫面。
`2` 不是量出來的最佳值 —— 它是一個保守且常見的上限，
真正的數字等 `FE-O12` 的效能預算。**那時候要改的是 Requirement，不是程式碼。**

### D5：卸載檢查用「全域監聽數量」，不用記憶體

規格 S08 斷言兩件事：**掛載期間的監聽數量曾經高於掛載前**（防恆真），
以及**卸載後回到掛載前的水準**。

**沒有用記憶體**：那是 `FE-W07` 的「重複進出十次記憶體不得成長」，
而且記憶體在 jsdom 裡量不準。監聽器數量是這一項真正能保證的東西 ——
一個殘留的 resize 監聽會讓整棵 3D 樹無法被回收，而它是數得出來的。

## 驗證方式

**逐條指名。沒有一條留白 —— 留白的話實際發生的會是「我看起來沒問題」。**

| Scenario | 怎麼證明 |
|---|---|
| `S04` `S05` 載入中的呈現 | **component test** —— 等待狀態是 DOM，jsdom 驗得到 |
| `S06` `S07` WebGL2 有無 | **component test** —— 偵測是純函式（D1），mock `getContext` 即可 |
| `S08` 卸載後沒有殘留監聽 | **component test ＋ 人工瀏覽器（V4）** —— 見下面的警告 |
| `S01` canvas 存在且尺寸不為零 | **人工瀏覽器**（V1）—— jsdom 沒有 WebGL，`<Canvas>` 掛不起來 |
| `S02` resize 與 DPR 上限 | **人工瀏覽器**（V2）|
| `S03` 陰影出現在畫面上 | **人工瀏覽器**（V3，截圖）—— 這條只有眼睛驗得了 |

### 人工瀏覽器驗證：做什麼、留什麼

**⚠️ 在 production build 上做（`npm run build` ＋ `next start`），不是 dev server。**
理由與 `fe-x01-appshell` 的 design 相同：dev server 的行為在失敗路徑上不一樣。

| # | 動作 | 要留的證據 |
|---|---|---|
| V1 | 開 `/world` | 截圖 ＋ canvas 的 `width`/`height` 屬性值（不為零）＋ console 無 error |
| V2 | 改變視窗尺寸 | 改變前後的 canvas 尺寸；並在 `devicePixelRatio` 為 3 的模擬下確認有效 DPR 不超過 `2` |
| V3 | 看畫面 | **截圖**：方塊在平面上留下陰影。這條沒有別的證明方式 |
| V4 | 離開 `/world` 再回來，重複三次 | console 無 error、沒有 WebGL context lost 警告，**並用 DevTools 的 Event Listeners 確認 `window` 上的數量沒有逐次疊加** |

**連到哪裡**：只連本機自己起的實例。不連任何共用實例（`AGENTS.md`〈測試環境隔離〉）。

### ⚠️ `S08` 的 component test 有恆真的風險

jsdom 沒有 WebGL，所以 R3F 的 `<Canvas>` 很可能**根本掛不起來** ——
那樣它就沒機會掛任何 `resize` 監聽，於是「卸載前後相等」變成 `0 == 0`，
**測試永遠綠，而且拿掉清理邏輯它也不會紅**。

`tasks.md` 5.2 那種負向驗證（故意掛一個不移除的監聽）只證明**計數器沒壞**，
不證明 R3F 的生命週期真的走完了。

所以 `S08` 多了一條斷言：**掛載期間的監聽數量必須曾經高於掛載之前**。
在 jsdom 裡達不到的話，那條測試會**失敗而不是靜靜通過** ——
那時就知道這條只能靠 V4，而不是誤以為它被自動化涵蓋了。

### 自動化證明不到的

1. **畫面上真的有東西。** `S01` 的 component test 版本最多只能斷言
   「元件沒有拋錯」，那跟「畫出來了」是兩回事
2. **陰影的品質。** V3 的截圖證明「有陰影」，不證明它好看 ——
   那是 `FE-W14` VisualPolish 的事
3. **效能。** 本次完全不量 FPS 或 draw call，那是 `FE-O12`／`FE-W13`

## Risks / Trade-offs

**R1｜`@react-three/fiber@9.7.0` 的 react peer 是 `>=19 <19.3`** →
本專案是 `19.2.8`，在範圍內但**接近上界**。升 React 之前要先確認 R3F。
緩解：把版本釘死並在 `package.json` 旁的說明寫明這個上界。

**R2｜three 進 bundle 之後首次載入的體積會跳一個級距** →
本次不量、也不最佳化（`FE-O12` 的範圍），但 **`FE-X01` 的 `ssr: false`
已經讓它是分開的 chunk** —— 不會拖累 `/world` 以外的頁面。
緩解：在 PR 上記錄 build 輸出的 chunk 大小當基準線，讓 `FE-O12` 有東西可比。

**R3｜渲染面的自動化測試在這一項缺席，而且會一直缺席到 `FE-O11`** →
每多一個 3D 項目，靠人工驗證的面積就大一塊。
緩解：把 V1–V4 寫成具名的表，`FE-O11` 決定工具之後可以逐條轉自動化。
**這個風險隨後續每一項累積，不會自己消失。**

**R4｜除錯用的平面與方塊可能活得比預期久** → `FE-W10` 在 W3，
中間隔著 `FE-W02`–`FE-W07` 五個項目，都會看到它。
緩解：檔名與註解直接寫明它由誰移除；不要用 `Floor` 這種正式名字。

## Open Questions

這些現在不答也不會改變規格、做法或任務拆解：

- **render loop 的更新策略**（每幀都畫 vs 有變化才畫）。`FE-O12` 的效能預算
  出來之前這是猜的，而且改它不影響任何一條 Requirement
- **陰影貼圖解析度與光源角度的實際數值。** 從外部觀察不出差別，
  `FE-W09`／`FE-W14` 定統一風格時會收斂
- **DPR 上限要不要從 2 改成別的。** 規格現在寫 `2`；`FE-O12` 量出來之後
  如果要改，**回去重開 spec PR**，不要就地改程式碼
