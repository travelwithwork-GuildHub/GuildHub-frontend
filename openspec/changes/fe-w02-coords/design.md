## Context

動機見 `proposal.md`，需求見 `specs/`。三個形塑做法的既有條件：

1. **合約在後端。** `GuildHub-backend/app/realtime/protocol.py` 的 `Move`：
   `x` / `y` 是 `StrictInt`，`f` 是 `StrictInt(ge=0, le=3)`，
   註解寫 `0=下 1=左 2=右 3=上`。依 ADR-0001，本 repo 不複述欄位定義。
2. **不合協定的訊息是靜默丟棄的。** `main.py` 收到 `ProtocolError` 是
   `continue` —— 不回錯、不斷線。所以錯誤必須在前端就明顯失敗。
3. **後端沒有任何座標範圍檢查。** `StrictInt` 沒有 `ge`/`le`，
   負數與極大值都會被接受。世界邊界是 `FE-W04` 的事，不是這裡的。

## Goals / Non-Goals

**Goals:**

- 讓 `FE-W03`／`FE-R03`／`FE-R07` 有**唯一一份**對映可以 import
- 讓「送出去被丟掉」這種無聲的失敗，在前端變成會拋錯的
- 每一條 Scenario 都是純函式測得到的 —— 這一項**沒有人工驗證**

**Non-Goals（設計層面）:**

- 不決定世界有多大（`FE-W04` 的 World Bounds）
- 不決定取樣頻率（`FE-R03` 的 ≤10 Hz）

## Decisions

### D1：比例定成 1 世界單位 = 32 協定像素

寫進 Requirement 而不是留給實作，因為它**可觀察**：比例決定量化的粒度，
而粒度直接影響遠端玩家看到的位置精度。

`32` 的理由：量化誤差是 ±0.5 像素 = ±1/64 世界單位 ≈ 0.016 ——
比任何人眼看得出的移動都小，而且 32 是 2 的冪，除法沒有二進位誤差。

**這個數字之後要改的話，改的是 Requirement，不是程式碼。**

### D2：世界 Z 對映到協定 y，不是世界 Y

3D 的 Y 是高度，不參與 2D 的 gameplay logic（`CONTEXT.md`：
「移動是 2D gameplay logic，3D rendering + 2D 邏輯」）。
遊玩平面是 X／Z，所以 Z 才是協定的 `y`。

**這一條寫錯的話症狀很難查**：本地玩家在 3D 裡走得好好的，
遠端玩家卻只在一條線上移動 —— 因為所有人的 `y` 都是高度（恆為 0）。

### D3：原點重合，不做位移

協定的 `StrictInt` 允許負數（沒有 `ge`），所以不需要把世界中心搬到
某個正數象限。原點重合是最少驚訝的選擇，而且省掉一個之後會被忘記的常數。

### D4：`.5` 往正無窮（`Math.round` 的行為）

任何確定性的取整都能滿足往返穩定性，所以這裡選的是**最不需要解釋**的那個。
寫進 Requirement 是為了讓它可被測試釘住 —— 不寫的話，
之後有人改成 `Math.floor` 也不會有東西紅。

代價：對負數不對稱（`Math.round(-0.5)` 是 `-0` 不是 `-1`）。
這不影響往返穩定性（那是對**整數**輸入的性質），但值得知道。

### D5：零向量回傳 `null`，不是預設朝向

「站著不動的角色不應該轉頭」是產品行為，但更重要的是**型別上的誠實**：
沒有方向就是沒有方向。回一個預設值的話，呼叫端不會知道要保留前一個朝向，
而症狀是角色一停下來就轉向同一個方向 —— 看起來像 bug，查起來像玄學。

### D6：非有限值與超出安全整數**拋錯**，不回退

`NaN` 送出去會被 `StrictInt` 擋下 → 整則訊息被靜默丟棄。
回一個 `0` 之類的「安全值」更糟：角色會瞬移到原點，而沒有人知道為什麼。

**拋錯是唯一會被看見的失敗方式。**

## 驗證方式

**這一項完全沒有人工驗證。** 每一條 Scenario 都是純函式，
`FE-W01` 的 `S01`–`S03` 那種「只有眼睛驗得了」的情況在這裡不存在。

| Scenario | 怎麼證明 |
|---|---|
| `S01`–`S03` 雙向對映 | 單元測試 |
| `S04` `S05` 往返穩定 | 單元測試（`S04` 掃一組含負數與零的值） |
| `S06` `S07` 明顯失敗 | 單元測試（`expect(...).toThrow()`） |
| `S08`–`S10` 朝向 | 單元測試 |

**負向驗證**（把防禦拿掉，測試要變紅）：

- 把 `Math.round` 改成 `Math.floor` → `S02` 要紅
- 把比例從 32 改成別的 → `S01` 要紅
- 把零向量的回傳從 `null` 改成 `0` → `S10` 要紅
- 拿掉非有限值的檢查 → `S06` 要紅

## Risks / Trade-offs

**R1｜這份對映是「唯一一份」，但沒有機器擋得住複製** →
`FE-W03`／`FE-R03`／`FE-R07` 任何一個自己再寫一次 `* 32`，兩邊就開始漂。
緩解：`proposal.md` 與程式碼註解都寫明；ESLint 沒有規則擋得住這件事，
**這一條只能靠 review**。

**R2｜比例 32 是猜的** → 它不是量出來的，是選一個 2 的冪。
如果之後 `FE-W04` 定的世界尺寸讓 32 顯得太粗或太細，要回去改 Requirement。
緩解：D1 寫明「改的是 Requirement，不是程式碼」。

**R3｜對角線的決勝規則是任意的** → 取縱向沒有產品上的理由。
緩解：規格明寫它是任意但必須固定，理由是「不固定的話沿對角線移動
會讓朝向跳動」。`FE-W03` 做出來之後如果手感不對，回來改 Requirement。

## Open Questions

- **世界有多大。** `FE-W04` 的 World Bounds 會定，而它會決定協定像素的
  實際範圍。不影響本項任何 Requirement —— 對映對任何範圍都成立。
- **`FE-R06` 的多分頁語意**（同一個人兩條連線互相覆寫位置）目前未定義。
  那不影響對映本身，但它會決定 `FE-R03` 送出什麼。
