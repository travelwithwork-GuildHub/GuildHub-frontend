## Context

見 proposal.md〈Why〉。這裡只記三件會影響實作與驗收的事實。

**後端的身分規則**（`app/main.py` 的 `_identify()`）：先看 session cookie 的
`user_id`，**沒有 session 就 `str(uuid.uuid4())`**。前端目前的 `/world` 是匿名連線，
所以**每建立一條連線就是一個新的人**。

**rAF 停止時已經發生的事**：位置同步、本地角色、遠端角色的 render loop
全部掛在 `useFrame` 上，所以背景時三者一起停。送出頻率自然變成 0 Hz。

**WebSocket 的 message 事件不受 rAF 影響**：背景時遠端玩家的樣本照樣寫入，
而寫入函式自己會清掉游標已經越過的舊樣本（`FE-R08` 的 pruning），
所以緩衝**有上界**，不會因為背景很久而無限成長。

## Goals / Non-Goals

**Goals**
- 把「不斷線、不降頻」這個決定寫下來，連同它的理由
- 修掉「按著鍵切到背景，回來角色自己走」

**Non-Goals**
- **不做重連。** 連線真的斷掉時要怎麼辦是 `FE-R12`（W5）的範圍
- **不做背景降頻。** rAF 停止就是降頻
- **不處理「背景很久回來之後畫面該演什麼」** —— 遠端角色的畫面位置是
  `evaluate(樣本, now − 250ms)` 的純函式，它不看上一幀，所以背景多久回來
  都會直接出現在正確的位置。這是 `FE-R08` 已經做完的事，不需要補救邏輯

## Decisions

### D1：不斷線（而不是「切到背景就關掉連線省資源」）

替代方案是「隱藏超過 N 秒就關閉，回到前景重連」。**否決**，因為匿名身分
是每條連線一個 uuid：重連＝變成另一個人。省下來的伺服器資源換來的是
「切個分頁回來就換了個身分」，而那在多人世界裡是使用者看得見的錯。

登入做出來之後身分會穩定，那時可以重新評估 —— 但那要重開 spec PR。

### D2：不新增背景降頻的程式碼

rAF 停止已經讓送出變成 0 Hz。再寫一套「偵測到隱藏就降頻」是在既有的 0 上
再加一層狀態機。**少一種狀態就少一種只在特定時序下出現、而且沒有錯誤訊息的 bug。**

### D3：三個事件都要清輸入，不是挑一個

`blur`、`visibilitychange`→`hidden`、`pagehide` 三者的涵蓋範圍**互有缺口**：

- 切到同一個視窗的別的分頁：`visibilitychange` 一定觸發，`blur` **不一定**
- 整個視窗失去焦點但這個分頁仍是可見的那一個：`blur` 觸發，`visibilitychange` **不觸發**
- 頁面進 bfcache：`pagehide` 觸發

清空按鍵狀態是**冪等**的（`pressed.clear()`），重複觸發沒有代價，
所以三個都掛的成本是零、漏掉任何一個的成本是「角色自己一直走」。

### D4：驗收在 jsdom，不在瀏覽器 —— 因為量不到

**headless Chromium 無法重現背景分頁。** 兩種方法都試過：

| 方法 | 結果 |
|---|---|
| `page.bringToFront()` 讓另一頁到前景 | 被切到後面那頁的 `document.visibilityState` **仍然是 `visible`**，rAF 照跑 42 FPS |
| CDP `Page.setWebLifecycleState` | `'hidden'` 不是合法值（只有 `frozen`／`active`）；送 `'frozen'` 之後 rAF 仍然跑了 2487 次／43 秒（約 58 FPS）—— **沒有真的凍結** |

所以這個 change 的自動驗收只能是 **jsdom 層**：派送真的 `visibilitychange`／
`pagehide`／`blur` 事件，斷言按鍵狀態被清掉、角色停下來。

**這不是把驗收降級，是承認工具的邊界。** 這些測試驗的是
「**我們的程式碼對這些事件的反應是對的**」；「瀏覽器在真的背景時會派送這些事件」
是平台的保證，不是我們能測的東西。

真實瀏覽器那一半是**人工檢查**，寫在 tasks.md 裡：按著方向鍵切到別的分頁，
等三秒切回來，角色應該是停著的。

## Risks / Trade-offs

- **長時間背景之後回到前景，累積的 WebSocket message 事件會一次處理完。**
  樣本陣列有上界，但**瀏覽器的事件佇列沒有**。10 Hz、幾分鐘的量級應該無妨，
  真的變成問題時要量了再處理（`FE-R09` 的負載測試會看到）。
  這一點是 codex 指出來的
- **行動裝置的作業系統可能直接凍結或殺掉分頁**，那時保活是不可能的。
  這種情況下連線會斷，走既有的關閉語意 —— 而 `FE-R12` 之前**沒有重連**，
  使用者會停在一個靜止的世界裡。**這個缺口是知道的，不是忘了**
- **`blur` 的既有行為在此之前沒有規格**。這個 change 補上它，
  代價是這條 Requirement 混了「新增」與「補記」兩件事 ——
  但拆成兩個 change 會讓「三個事件互相補位」這個唯一重要的理由被切開
