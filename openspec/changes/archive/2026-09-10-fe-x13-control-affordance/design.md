# `FE-X13` design

## M1 量測：這個專案的 design token 各自有多少對比度

分歧不裁決，**去量**。用 Playwright 把 `@theme` 裡的 token 畫到 canvas 上
讀 pixel，換算成 sRGB 之後算 WCAG 對比度：

```
token            sRGB                對 surface 的對比度
surface          rgb(247, 248, 251)  —  （body 的底色）
surface-raised   rgb(255, 255, 255)  1.06:1
line             rgb(219, 222, 227)  1.27:1
accent           rgb( 55, 120, 215)  4.09:1
danger           rgb(204,  51,  51)  4.84:1
ink-muted        rgb( 98, 105, 117)  5.21:1
ink              rgb( 26,  32,  41)  15.42:1

白色文字對 accent 底                  4.35:1
```

⚠️⚠️ **量測本身有一個坑，而它會靜默給出錯誤答案。**

`getComputedStyle(el).color` 對 `oklch()` 的值**原樣回傳字串**
（Chrome 不轉成 rgb）。第一版的量測腳本直接 parse 那個字串，
於是抓到的是 `0.98 / 0.004 / 260` 這三個數字 —— 結果 `line` 與 `ink`
都算出 **1.00:1**，而那個數字看起來完全合理（「深色對淺色沒有對比」很怪，
但「淺灰對白沒有對比」不怪）。

**判準的實作 SHALL 把顏色實際畫出來再讀**（canvas `fillStyle` ＋
`getImageData`，或 `getComputedStyle` 之後再過一次 canvas），
不可以直接 parse 字串。

## D1 判準量什麼

在真的瀏覽器上，對每個啟用中的控制項：

1. `getBoundingClientRect()` 確認有非零面積
2. 取 `background-color` 與四邊的 `border-*-width` / `border-*-color`
3. **把半透明顏色與實際底色做 alpha compositing**，再算 WCAG 對比度
4. 至少滿足一條：填色達 `3:1`，或某一側有寬度 `≥ 1px` 且合成後達 `3:1` 的 border

⚠️ **`1px solid transparent` 合成後對背景是 `1:1`，因此不會誤過。**
這是刻意檢查的作弊路徑 —— 只看 `border-width > 0` 的判準會被它騙。

⚠️ **判準 SHALL NOT 出現色碼、Tailwind class 名稱、padding 或元件尺寸。**
那會把今天的臨時外觀變成沒有經過規格決定的永久契約。

## D2 為什麼門檻不是「alpha > 0」

第一輪時一位審查者提的門檻是「`border-width > 0` 且 `border-color` 的
alpha > 0，或 `background-color` alpha > 0 且與父層不同」。

**M1 的數字直接推翻了它**：現有的 `line` 是 `1.27:1`、白底是 `1.06:1`，
兩者都「不透明而且與父層不同」。照那個門檻做完，測試會綠，
**而使用者看到的東西幾乎沒變** —— 那正是這一列被開出來的原因。

第二輪把數字交回去之後，該審查者撤回，兩邊在 `3:1` 上達成共識。

## D3 為什麼輸入框在範圍內（`docs/WBS.md` 沒寫）

WBS 上這一列只提到按鈕。**使用者的原話是「登入畫面也太醜了 / 輸入匡也看不到」。**

兩個外部審查者被獨立問到「空白、未聚焦的文字輸入框，它的邊框算不算
WCAG 1.4.11 所說的『識別該元件所必需的視覺資訊』」，**兩邊都答「算」**。

理由：按鈕有文字，外觀被清光時畫面上至少還有字；
**空白的輸入框沒有任何內容**，「有沒有東西在那裡」只能靠填色或邊界本身。

`docs/WBS.md` 的敘述要補，但那要另一個 `governance/` PR。

## D4 為什麼 `3:1` 寫進 Requirement，而不是只留在判準裡

⚠️ **這一條在第三輪才收斂，而且是兩邊各自改過口的結果。**

一邊主張不寫進規格（「規格是行為規格，不綁死實作與測試手法」），
方案是把數字放進「測試約定」。

另一邊主張要寫，逐字：「這不是 class、色碼或測試手法，而是**使用者可觀察
行為的最低門檻**。若 Requirement 只寫『清楚可見』，測試中的 `3:1`
就會成為**沒有規格根據的隱藏契約**。」

**決定性的事實是這個專案的治理形狀**：`openspec/` 的改動要經過 PR 審查、
有 CI 擋、Scenario ID 進 main 之後就是穩定鍵；而**測試檔案裡的常數
任何人都能在一個實作 PR 裡順手改掉**，不需要任何規格流程。
把 `3:1` 放在「測試約定」裡，擋不住「某人把它改成 `1.2:1` 讓測試變綠」。

第三輪時主張不寫的那一方撤回，逐字：「我先前的方案確實與『隱藏契約』
沒有差別。」

## D5 新增一個 token，`line` 不動

`3:1` 讓現有的 `--color-line`（`1.27:1`）不合格。三個選項：

| | 做法 | 後果 |
|---|---|---|
| (a) | 直接改 `--color-line` 的值 | `line` 同時用在分隔線與卡片邊界上，**那些不需要 3:1**；改了會讓整個介面變重 |
| (b) | 新增控制項邊界專用的 token | 修改半徑收在互動控制項上 |
| (c) | 降低門檻 | 重新放過「輸入框看不到」 |

**兩個審查者獨立選 (b)。** 這一列只新增**一個**語意 token，
套到本列涉及的按鈕與輸入框，**SHALL NOT 全面替換既有的 `line`**。

## D6 範圍限制（兩個審查者的答案完全一致）

被獨立問到「這一列只有 3 點，最可能做錯的決定是什麼」，兩邊都答了同一件事：
**把這次修補升級成完整的表單／設計系統重構。**

所以 `proposal.md` 的〈不做什麼〉那一節是規範性的，不是客套話。
順手統一欄位尺寸、間距、錯誤狀態、focus、disabled、responsive layout，
或建立帶 API 的 `<Button>` / `<Input>`，就是把 `FE-X05` 偷塞進 3 點工作。

## V 驗證

- **V1** `/login` 與首次進入流程上，每個啟用中的按鈕都達 `3:1`（`S01`／`S02`／`S06`）
- **V2** 兩個畫面上每個空白、未聚焦的輸入框都達 `3:1`（`S04`／`S06`）
- **V3** 一個「只有 1px 透明邊框」的控制項 SHALL 不通過 V1（`D1` 的作弊路徑）
- **V4** 一個「只有 `surface-raised` 白底」的輸入框 SHALL 不通過 V2（`S05`）
- **V5** `disabled` 與啟用中的按鈕外觀可區分（`S08`）
- **V6** 共用的外觀定義只有一處，改它會同時影響兩個入口（`S07`）

### 突變（驗收條件）

⚠️ **不是「測試全綠」，是「把防禦拿掉，測試要變紅」。**

- **X1** 把共用外觀的 `className` 整個移除 → V1、V2 要紅（`S03`）
- **X2** 把控制項的邊界換成 `--color-line`（`1.27:1`）→ V1、V2 要紅
- **X3** 把輸入框的邊界換成 `surface-raised` 白底（`1.06:1`）→ V2 要紅
- **X4** 判準改成只檢查 `border-width > 0` → X2、X3 要變成抓不到
  （**這一條驗的是判準本身，不是產品**）
- **X5** 只修 `/login`、不動首次進入流程 → V6 要紅
