# design：`FE-A01 登入與 session`

五個決定，全部經過 codex `gpt-5.6-sol` 與 Antigravity CLI `Gemini 3.1 Pro (High)`
兩輪討論。**第一輪五題中兩題不一致，第二輪把彼此的理由餵給對方之後收斂。**
不一致的那兩題與收斂的過程逐條記在下面 —— 不記的話，之後有人翻案時
會重跑一次同樣的討論。

---

## D1：範圍只到匿名 ＋ 恢復金鑰，不含帳號密碼

後端在 9/8 長出了 `POST /api/register` 與 `login_id`+`password` 登入（L3 裁決），
所以 `POST /api/login` 現在是**三選一**：`nickname` / `resume_token` /
`login_id`+`password`，多給少給都 422。

`docs/WBS.md` 的 `FE-A01` 工作欄只寫「匿名暱稱登入、session 保存、重整恢復」。

**選 (a)：只做匿名 ＋ `resume_token`。** 兩個模型第一輪就同意。

- 做進帳密＝**擴張一份已經估過點數的範圍**，而那張表只有 `governance/` 能改
- 只做匿名、連 `resume_token` 都不做，則**處理不了 WBS 第二列**
  （「cookie 被清除後的行為」）—— 那一列不是選配

帳密與註冊要走 `governance/` 另開項目。**不在本 change 裡順手做。**

## D2：恢復金鑰預設不落地

`resume_token` 就是 `ProfileOut.id`（一個 UUID）。後端註解逐字寫著：

> **它不是驗證身分**：拿到 token 的人就是那張名片的人。

也就是說它是一枚 bearer secret，而前端要讓「清 cookie／換裝置回得去」成立，
就得把它存在某個地方。

**⚠️ 第一輪兩邊不一致：**

| | 主張 | 理由 |
|---|---|---|
| codex | (c) 勾「記住我」才存 | 預設不落地 bearer secret |
| Gemini | (a)+(b) **必須**存 ＋ 展示救援金鑰 | 「只存 localStorage 卻不告知，一旦清除瀏覽器資料帳號即永久死亡」 |

**第二輪收斂到 codex 的預設，但採納 Gemini 的告知義務。**
讓 Gemini 改變主張的是一個第一輪沒送到它面前的事實：
**後端 9/8 已經有帳號密碼註冊** —— 想要真正持久身分的人**有另一條路**，
只是那條路不在 `FE-A01` 範圍內（D1）。匿名登入因此可以回到
「輕量、暫時」的本質，不必自己扛「永久帳號」的責任。

處置：

- 預設**不寫** `localStorage`
- 勾「記住我」才寫，並明說**這擋不住 XSS**
- 金鑰本身顯示出來、可複製（Gemini 的「救援金鑰」）
- 「未勾、也未備份 → 清掉 cookie 之後回不去」是**使用者的知情選擇**。
  codex 的但書逐字保留：**「若 UI 默默如此，才是發表日災難」** ——
  所以告知是義務，不是提示

## D3：那條缺席的判準要約束**實際路徑常數**，不是只驗 schema

`getMyProfile` 打了一個不存在的端點，而抓得到它的資訊一直在 repo 裡
（`schema.d.ts` 寫著 `"/api/profiles/me": { get?: never }`）。

兩個模型都同意判準要在**型別層**（`CLAUDE.md` 與 `AGENTS.md` 都明文寫
**CI 不提供任何服務**，所以不能靠打真後端）。

**但兩邊提的形狀不一樣，而 codex 明確否掉了 Gemini 的：**

Gemini 提的是獨立斷言：

```ts
type _AssertGetMe = paths['/api/me']['get']
```

codex 的裁決逐字是：

> **只驗 schema、卻未約束實際路徑常數：不合格，因為 production code 改錯仍可能綠。**

—— 而它是對的。上面那條斷言證明的是「後端有 `GET /api/me`」，
**證明不了 `getMyProfile` 用的是它**。`operations.ts` 裡的字串照樣可以是任何東西。
這正是今天這個 bug 的形狀：資訊在、斷言不在；再寫一條不綁生產碼的斷言，
只是把同一個洞換個位置。

**採用的形狀**：把 `RequestSpec` 的 `path` 收窄成
「產出型別檔中、該 method 確實存在的路徑」的聯集，讓 `operations.ts` 的每一個
呼叫點在 typecheck 時就被綁住。

```ts
type PathsWith<M extends string> = {
  [P in keyof paths]: paths[P] extends Record<M, infer Op>
    ? (Op extends undefined ? never : P) : never
}[keyof paths]
```

驗收（`AGENTS.md`：**拿掉防禦，測試要變紅**）：

| 動作 | 必須 |
|---|---|
| 把 `'/api/me'` 改成 `'/api/mee'` | 紅 —— 不在 `paths` 的鍵裡 |
| 改回 `'/api/profiles/me'` 配 `GET` | 紅 —— 它的 `get` 是 `never` |
| **把判準本身刪掉** | 兩邊都確認：**沒有任何別的東西會紅** |

最後一列要寫進規格。**它是唯一的守門員**，而唯一的守門員被刪掉時
沒有人會知道 —— 這正是 `FE-O01-S10` 那條涵蓋率斷言存在的理由，
同一個道理套在路徑上。

## D4：登出寫成已知限制，不寫成 Requirement

後端**沒有 logout 端點**（`grep -rn 'logout\|session.clear\|session.pop' app/` 是空的），
而 session 是 HttpOnly cookie，前端 JS 清不掉。

兩個模型都同意：**現在就寫下來，但寫成限制，不是假裝完成了登出。**

codex 的理由是「這是 A01 的 session 邊界」；Gemini 補了一條更實際的：
不白紙黑字寫明的話，**驗收的人會因為「無法登出以測試重新登入」而卡關**，
然後把它當成 A01 的 bug。

真正的清除 session、登出 UI 與驗收仍屬 `FE-A02`，
而且 `FE-A02` 要能完成，**後端必須先補 logout 端點**（要開一張後端票）。

## D5：`/world` 不擋，導流留給 `FE-A06`

**⚠️ 第一輪兩邊不一致：**

| | 主張 | 擔憂 |
|---|---|---|
| codex | (b) `/world` 匿名可進、顯示「訪客」 | 把 `FE-A06` 的導流**偷塞進** `FE-A01` |
| Gemini | (c) 進入前強制輸入暱稱 | 允許訪客的話，發表日「每個人有名字」**破局** |

**第二輪兩邊都同意中間解**：`FE-A01` 只做「登入本身 ＋ `/world` 顯示目前身分」，
`FE-A06`（6 點、同樣是 W2、可以緊接著做）才做「進入前的導流」。
發表日的硬目標由 `FE-A06` 交付，不由 `FE-A01` 交付。

**codex 加了一個條件，而它不是形式上的：**

> 唯一條件是：**`FE-A06` 必須列為發表前阻擋項目**。
> 若發表版本可能只交付 A01、不交付 A06，Gemini 的擔憂仍成立；
> 但解法是管理依賴與 release gate，不是把 A06 偷塞進 A01。

—— 這件事要落在 `docs/WBS.md` 上（`governance/` 分支），不是落在這份 design 裡。
**沒落上去的話，這個中間解就退化成 codex 原本反對的那個版本。**

## 兩邊各自提的「第六件事」，以及查證結果

第一輪最後問了兩邊「你們沒被問到、但不決定就會錯下去的一件事」。
**它們講了不同的兩件，而查證之後兩件都不進本 change 的 Requirement：**

**codex：前後端的 cookie 部署契約**（同源與否、`credentials`、`SameSite`/`Secure`）。
查證：`src/config/env.ts` 已經有 `REST_CREDENTIALS = 'include'`，`transport.ts` 每個請求
都帶它且已有測試；後端也已經有 `COOKIE_CROSS_SITE` 開關，而且在
`CORS_ORIGINS` 有非本機來源卻沒開該開關時會**啟動失敗**並印出
「登入成功，然後每個 API 都 401」。**兩邊都已經處理了，而且部署還沒發生。**
→ 處置 (iv) 什麼都不做；部署網址確定後放進部署驗收清單。

**Gemini：`drift.ts` 為什麼沒紅？** 它推論「要麼 `schema.d.ts` 沒同步、
要麼比對實作有嚴重漏洞」。查證：是前者，**而且是設計上的**。
`GENERATED.md` 檔頭就寫著「它會過期而且不會有人告訴你，重產是人為動作」，
排程在 `FE-O08`（W5 起）。後端此後前進了 6 個 commit。
→ 處置：本 change 重產一次（`schema.d.ts` 進 `LoginIn` 的 `resume_token` 要靠它），
**自動重產／新鮮度比對另開票**。

⚠️ **這一段記在這裡的理由**：Gemini 的推論從「哨兵是綠的」直接跳到
「實作有漏洞」，而正確答案是「它綠得合乎設計，代價是後端動兩天沒有聲音」。
**兩個結論的處置完全不同** —— 前者要修 `drift.ts`，後者要開一張機制票。
不查證就照單全收的話，會去修一個沒有壞的東西。

## 測試會連到什麼

**不適用：測試不連任何外部服務。**

- 單元／整合測試用 `vitest`，`fetch` 由測試替身接管，不出網路
- 型別層的契約判準是 `tsc`，不需要任何服務
- 人工瀏覽器驗證打的是**自己在本機起的** GuildHub-backend
  （`~/Desktop/workshop/fergus/GuildHub-backend`，`bash run.sh`）
  —— `AGENTS.md`〈測試環境隔離〉：**MUST NOT 連任何團隊共用位址**

## 第三輪：規格寫完之後送兩邊審，改了六處

**規格自己會錯，而且這次錯了六處。** 記在這裡是因為其中三處的形狀
是這個 repo 反覆出現的 —— 不記的話，下一份規格會再犯一次。

| # | 誰抓到 | 問題 | 處置 |
|---|---|---|---|
| 1 | codex | **`S05` 與 `S08` 矛盾** | `S05` 加上「且沒有可用的恢復金鑰」 |
| 2 | 兩邊 | **`S07` 恆真** | 補上反方向：勾了記住我就 SHALL 出現 |
| 3 | codex | `S04`／`S12` 沒守住「真的去問後端」 | 兩條都補上「後端改了名字就要跟著變」 |
| 4 | codex | **完全缺一條「找得到登入入口」** | 新增 Requirement ＋ `S16` |
| 5 | Gemini | **完全缺「手動輸入金鑰」的成功路徑** | 新增 `S17` |
| 6 | Gemini | `S12` 會在 `FE-A06` 做完之後變紅 | 拿掉「SHALL NOT 導向登入」 |

**第 1 條是最貴的那種錯**：它會讓**正確的實作變紅**。
cookie 不在的時候 `GET /api/me` 必然先回 401，而那正是要拿金鑰去恢復的時刻；
無條件要求「顯示訪客、不重試」等於規定實作不准恢復。
`FE-W12` 的 `S11` 犯過同一種錯，這是第二次。

**第 4 條與 `FE-W12` 漏掉「門看得出來是門」完全同型**：
每一條 Scenario 都從「使用者送出暱稱」開始，也就是**假設他已經找到了入口**。
可以做出一個判準全綠、而入口根本看不見的產品。
⚠️ 那次是**人工截圖**才抓到的，這次是審查抓到的 —— 但只差一步。
**tasks 的人工驗證那一節不能省。**

**第 6 條是我製造的跨 change 衝突**：我把「SHALL NOT 導向登入」寫成了 `FE-A01`
的義務，而 `FE-A06` 的全部工作就是導向登入。留著的話，`FE-A06` 得先發一個
`## MODIFIED Requirements` 把它拿掉才能開工。
現在的寫法只保證「沒有身分時世界不會壞掉」，把「擋不擋」整件事留在 `FE-A06`。

**另外一條沒有改的**：codex 說 Requirement 裡「前端 SHALL NOT 自行保存任何等同於
『已登入』的旗標」是**實作結構不是產品義務** —— 它是對的（`FE-W12` 被指出過
同型的一條）。處置是把那句話換成可觀察的形式：
**「後端上那張名片的名字改變之後，重新進入應用 SHALL 顯示新的名字」**。
同一個約束，但它現在是使用者看得到的事，而且測得出來。
