# 設計

三輪與 `codex gpt-5.6-sol`、`Antigravity CLI 的 Gemini 3.1 Pro` 討論之後，
兩邊都明確寫了「我同意這份草稿可以合併」。這裡記的是**取捨與被推翻的東西**。

## D1：配置是資料，不是 JSX

三個選項：一份資料表、直接寫 JSX、混合（結構用 JSX、可擺設的用資料表）。

**兩位都選資料表，而且都指出混合案是陷阱**：牆與走廊同樣需要 transform 與
碰撞推導，把它們留在 JSX **仍然會產生第二份空間真相**。

Gemini 補了一個我沒想到的角度：JSX 的話，物理層要的 `StaticBox[]` 得從
React tree 裡「萃取」出來 —— 那會扯上掛載順序與 ref 的生命週期，
而且違反 `world-environment` 明訂的「場景元件 MUST NOT 建立碰撞體」。
**資料表可以在進入 React 之前就 map 出碰撞清單。**

形狀是 discriminated union，每一項帶**穩定的識別字**：

```ts
type LayoutItem =
  | { id: string; kind: 'wall';   x: number; z: number; turns: QuarterTurn; length: number }
  | { id: string; kind: 'desk';   x: number; z: number; turns: QuarterTurn }
  | { id: string; kind: 'project-board'; x: number; z: number; turns: QuarterTurn }
  // …
```

**識別字為什麼不是陣列索引**：插一段牆進去，後面每一項的身分都變了。
而「四個邊界各註冊一次」這種判準失敗時，訊息會說不出是哪一個。

## D2：世界改成 24×24 —— 但理由不是「遮住視野」

`PHYSICS.halfExtent = 10` 的檔頭寫「暫定值，遊玩區域的真正尺寸由 `FE-W11` 定」。

Gemini 第一輪主張維持 20×20，理由是「玩家**不應該**一眼看穿整個大廳，
這樣分區才有探索感」。**我去量了那個前提**：

```
orthoFrustum: halfHeight = viewHeight / 2；halfWidth = halfHeight × aspect
viewHeight = 12，相機偏移 {x:0, y:12, z:12} → 俯角正好 45°

投影到地面：  縱向 12 ÷ sin(45°) ≈ 17.0 單位（Z）
              橫向 12 × 1.69     ≈ 20.2 單位（X）
```

**看得到的地面約 20 × 17，而世界是 20 × 20。** 截圖確認四面牆同時在畫面四個邊緣。
**前提不成立 —— 20×20 現在就是一眼看完的。**

Gemini 看到數字之後改口。兩邊接著同意一件更重要的事：
**「一眼看到活動分布」不是缺點。** `CONTEXT.md`〈3D 憑什麼存在〉那條鏈是
「看見 → 靠近 → 旁聽 → 打招呼 → 正式申請」——**看見是第一環**。
玩家不該先迷路才能社交。codex 的說法：遠處看得到人群與區域輪廓，
靠近之後才辨認具體內容，這才是對的。

所以 24×24 的理由換成**空間與動線餘裕**（spawn、兩個看板、社交區、走廊，
而 `FE-W12` 的門要沿走廊排）。**不跳到 30×30** —— 那會讓人與設施的密度稀掉。

**動的是世界不是相機。** `viewHeight = 12` 是 `FE-W05` 量出來的
（一開始寫 20，角色只佔畫面 8%，「那一項會做不下去」），
調小它會同時放大角色、打破 W05 已經確認的構圖。

**世界尺寸要有測試釘住，相機參數不用** —— 前者是空間契約（碰撞、生成位置、
容量都以它為單位），後者是視覺選擇。這條界線沿用 `FE-W05` 的先例。

## D3：邊界改由配置提供，而切換必須是原子的

三個選項：`createPhysicsWorld` 收 `StaticBox[]`（邊界也走這條路）、
保留 `addBounds` 只註冊非邊界、配置完全不註冊碰撞。

**兩位都選第一個**，而且都認為那是**收斂不是擴張**：對物理引擎來說本來就
不存在「世界的殼」與「裡面的牆」的區別，它們全是靜態盒子。
保留 `addBounds` 的話，世界幾何會散在三個地方（`halfExtent`、`addBounds`、配置），
而「證明沒有重複」只能靠分類規則，沒有消除雙軌。

⚠️ **這裡差點做出一個會讓 main 壞掉的切法。**
Gemini 第一版的四刀是：第二刀「修改簽名、**拔掉 `addBounds`**」，
第四刀「把配置傳進去」。codex 指出：

> 其中一個狀態**不是沒有邊界，就是雙重邊界**。
> 契約規格可以獨立先合，但**產品變更必須在同一個 PR 原子完成**。

Gemini 承認了（`/world` 已對外公開，`AGENTS.md` 規定 main 永遠可發佈）。
最後兩邊給出同一個兩步法：

1. 先加「可以收 `StaticBox[]`」的能力，**保留舊的邊界行為當 fallback**，
   新舊**互斥**（明確二選一，不能兩者默默同時生效）
2. 在**同一刀**裡改用配置的碰撞盒 **並且**拔掉 fallback

## D4：分區只給矩形

`FE-W12` 要依 `GET /api/rooms` 沿走廊生成 Project Door。
如果分區只是「一群東西剛好擺在一起」，`FE-W12` 只能憑空猜座標，
或者跟某張桌子的位置強耦合。

所以分區是**具名矩形**。但**到此為止**：

codex 第一輪建議再帶 `{ origin, axis, spacing, capacity }` 給 `FE-W12` 用。
我指出 `capacity` **今天沒有讀取者** —— 那正是 `FE-W10` 一起否決過的
「沒有呼叫端的抽象」。**codex 自己改站對面**：

> 尤其 `capacity` 今天沒有讀取者，會重犯 `FE-W10` 否決過的問題，
> 也會提前決定 `FE-W12` 的門排列模型。

**也不帶 sensor。** 「玩家走進 Board 區時系統知道」是互動語意，
今天沒有產品需求要它，而它會引入事件生命週期、重疊優先序與 UI 狀態。
需要的那天可以從同一份矩形幾何派生。

## D5：怎麼證明大廳真的可用

四條判準，三條是構圖、一條是連通性。

**構圖一律用正交投影算，不用像素比對**（`FE-O13` 還沒決定視覺回歸怎麼做），
而且**要固定長寬比** —— 不固定的話判準會隨測試環境漂移，或者直接恆真。

1. **出生時兩個看板在畫面內** —— 互動鏈的第一環
2. **關鍵站位上角色不被遮住** —— 相機在角色上方且 +Z 側，所以角色 +Z 方向的
   高物件會擋住它。**這是俯視角最常見的體驗缺陷，而它算得出來。**
   ⚠️ codex 特別警告：**不要寫成「玩家 +Z 一定距離內不得有高物件」那種粗略規則**
   —— 相機同時有 Y 與 Z 位移，遮擋取決於高度與距離的組合。
   要算的是「相機到角色的視線段有沒有穿過不透明物件的包圍盒」，
   而且只驗**設計上保證的站位**（出生點、兩個看板前、社交區、走廊入口），
   不要試圖證明所有連續座標 —— 那會把單元測試變成脆弱的幾何搜尋器
3. **走到極值仍然看得到地板** —— 見 D7

**第四條是 codex 提的，Gemini 沒想到**：把所有會擋路的盒子依角色半徑膨脹之後，
**出生點到每一個分區都要存在可走路徑**。

> 這比「看得到」更能證明 Guild Hall 真的可用，也能抓到
> **Door 周圍牆段意外封死入口**的錯誤。

而那種錯誤在渲染出來的畫面上**看起來完全正常**。

## D6：BFS 的解析度 —— 以及一個被撤回的提案

Gemini 提議**把 layout 的座標硬性對齊 0.5 網格**，BFS 也用 0.5 格，
理由是「這把尺絕對精準，不會有 0.6 過得去但格子說不行」。

**兩個問題**（我指出第一個，codex 補了第二個）：

1. `FE-W10` 的家具尺寸是 1.6／1.08／0.44 這類數字，**全部不對齊 0.5** ——
   等於要求所有元件重新定尺寸。**把測試實作的方便升格成整個 layout 的設計約束。**
2. 就算所有盒子的邊界對齊 0.5，**玩家半徑 0.25 膨脹後的邊界會落在 0.25 偏移上**
   —— 「0.5 絕對精準」本來就不成立。而且 0.5 格與玩家直徑相同，解析度太粗。

Gemini 撤回，稱之為「我的盲點：測試工具應該去適應真實世界的資料，
而不是反過來要求真實世界長成測試工具喜歡的樣子」。

**採 codex 的方案**：

- 格子 **0.1**（24×24 約 57,600 格，對靜態測試很輕）
- 障礙先按角色半徑 **0.25** 做 Minkowski 膨脹
- **四方向** BFS（避免斜向穿過障礙物的角落）
- **保守判定**：格子或移動邊只要接觸／相交膨脹後的障礙就算不可走
  —— **寧可誤報封閉，不要把走不過去的判成可走**
- 另外約束**主要通道明顯寬於角色直徑（至少 1.0）**。
  **不要讓判準去證明「0.6 的通道理論上剛好過得去」** ——
  那種通道在真的走起來時會一直卡住

**第三條路（visibility graph，不用格子）兩邊都反對**：它沒有消除精度問題，
只是把「格子解析度」換成「接觸邊界算不算相交、共線與退化角點怎麼處理、
epsilon 怎麼定」，實作與除錯成本更高。
未來地圖變大或改成程序化生成時再換。

## D7：地板 overscan，不 clamp 相機

**今天線上就會發生**：視覺地板的尺寸正好等於 `halfExtent × 2`，
所以玩家走到邊緣時，畫面上一定看得到地板外面的空白。

兩個修法：把相機 clamp 在安全範圍內，或者把視覺地板畫得比碰撞邊界大。
**兩位都選後者**：clamp 會讓玩家貼牆走時角色從畫面中心滑向一側，
**破壞固定跟隨相機的體感**，而那個體感是 `FE-W05` 已經確認過的東西。

⚠️ overscan 的大小 **SHALL 由相機投影到地面的範圍推導**，
不要寫一個隨手挑的常數 —— 相機參數改的那天，隨手挑的常數會靜默失效。

## D8：`world-physics` 不需要 MODIFIED delta

既有 Requirement 逐字：「系統 SHALL 在遊玩區域四周設置靜態邊界。
角色 MUST NOT 走出邊界。**邊界 SHALL 用與其他障礙物相同的機制（靜態 collider）**」。

**產品義務完全沒有改變**，而最後那句話反而**支持**這次的改動。
`FE-W04-S04` 的 ID 與 WHEN／THEN 都不動 —— 使用者可觀察的行為沒有變，
而且它應該繼續通過。

codex 的理由值得逐字留著：

> `addBounds` 是內部實作來源，不是規格契約。
> 若新增 delta 去描述 collider 由哪個函式或配置提供，
> **會把實作細節錯誤提升成產品義務**。

  這一項只提供走廊的矩形（見 D4）

  「`<group scale={2}>` 會讓視覺與碰撞脫鉤」的判準交給註冊碰撞的那一刻。

  但 `GuildHall` 元件外面仍然可以被別人包一層 `scale`。
  **要不要在註冊時檢查 world scale，留給第一個真的需要縮放的人**

  —— `FE-W11-S10`（走得到）擋得住「洞太窄或沒有洞」，
  但擋不住「洞比門寬很多」（看起來牆缺一角）
