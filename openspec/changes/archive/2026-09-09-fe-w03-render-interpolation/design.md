## 量測

### M1 —— 抖動的形狀（真 Chromium，production build）

用 `addInitScript` 裝上 `__THREE_DEVTOOLS__` 取得 Scene，找到角色的 root，
按住 ArrowRight，逐幀取 `position.x`，150 幀：

```
影格間隔中位數 16.70 ms（約 60 Hz）
一步的位移 = MOVE_SPEED(4) × fixedStep(1/60) = 0.0667

0.0667 0.0667 0.1333 0.0667 0.0667 0.0667 0.1333 0.0667 0.0667 0.1333
0.0667 0.0667 0.0667 0.1333 0.0667 0.0667 0.0667 0.1333 0.0667 0.0667
```

分布（120 幀）：**0 步 35 幀、1 步 66 幀、2 步 18 幀**。

**這不是效能問題** —— 畫面一直是 60 fps，掉的不是幀，是位移的均勻性。

### M2 —— 插值之後的不變量（數值模擬，可以手算驗證）

設速度 `v`、固定步 `h`、累積經過時間 `T`、已跑步數 `N`、`α = remainder / h`：

```
畫面位置 = prev + (cur − prev)·α
         = v·h·(N−1) + v·h·α
         = v·h·(N−1) + v·h·(T/h − N)
         = v·T − v·h
```

**畫面位置是「真實位置延後剛好一個固定步」的線性函數。**
於是逐幀的 `(畫面位移 / dt)` **恆等於 `v`** —— 不是近似，是恆等。

模擬（含抖動的影格間隔）：

```
dt=0.01667 steps=1 α=0.00  render=0.0000
dt=0.01733 steps=1 α=0.04  render=0.0693  rate=4.000
dt=0.01617 steps=1 α=0.01  render=0.1340  rate=4.000
dt=0.01750 steps=1 α=0.06  render=0.2040  rate=4.000
```

沒有插值的話，同一組 dt 下 `rate` 會是 0、4 或 8。**這就是判準**（D5）。

### M3 —— 分頁切回前景那一幀

```
dt=3.0    steps=5 α=0  render=0.4000  delta=+0.3333  rate=0.111
dt=0.0167 steps=1 α=0  render=0.4667  delta=+0.0667  rate=4.000
```

**delta 是正的。** 下一幀 `rate` 立刻回到 4。見 D4。

## 決策

### D1 —— render interpolation，不是別的四種

| 做法 | 為什麼不 |
|---|---|
| 把 `fixedStep` 改小（1/120） | 只是讓誤差變小不是消除；144 Hz 螢幕照樣抖 |
| 不用固定步，直接用 render dt 步進物理 | 固定步是刻意的 —— 影格率不穩時 character controller 的解算會抖，`FE-W04` 已經談定 |
| 對畫面位置做低通濾波／damp | 引入漂浮感與操作延遲，而且延遲量不確定 |
| 外插（用速度預測 `remainder` 之後的位置） | 撞牆時會先穿牆再被拉回，換成一個更難看的抖動 |

插值的代價是**最多一個固定步（16.7 ms）的視覺延遲**。
對「按方向鍵走路」這種操作那是一幀，量級遠低於它消掉的抖動。

### D2 —— 相機跟隨的目標換成畫面位置

**這一條漏掉的話，整個修法有一半沒有效果。**

相機用 `damp` 跟隨 `targetRef`。如果 `targetRef` 仍然寫物理位置，
相機的輸出會帶著同一個 0/1/2 步的節拍（damp 只把它變低頻，不會消掉），
而角色本身是平滑的 —— **於是角色相對於相機在抖**，
而使用者的眼睛鎖的正是角色。

### D3 —— 走路動畫繼續用 raw dt

現在的不一致是：位置走固定步、動畫相位走 raw dt。
直覺會想「一起改成固定步」。**不要。**

插值之後畫面位置等效於「以真實速率平滑前進」（M2 的恆等式），
而 raw dt 的動畫相位也是以真實時間前進 —— **兩者本來就咬合**。
把動畫改成固定步反而會讓腳步變成 0/1/2 的節拍，
也就是把剛修好的問題搬到腳上。

### D4 —— 不加 dt 的上限

諮詢時有人主張：`planSteps` 在被 `maxStepsPerFrame` 砍掉時把 `remainder`
設為 0，做插值之後 `α` 會突然變 0，**角色會被往回拉、產生嚴重抽搐**，
所以要在 render loop 開頭 clamp `dt`。

**數值模擬過（M3），那條是錯的。** `α = 0` 時畫面位置是 `prev`，
也就是「第 N−1 步之後的位置」；而 N 已經往前跳了 5 步，
所以那一幀的位移是 **+0.3333（往前）**，不是往回。
而且它是一次性的偏移 —— 下一幀 `rate` 立刻回到 4。

那一次不連續是**無法避免的**：分頁在背景待了三秒，物理不可能真的補三秒。
加一個 dt 上限只是換一個地方丟掉同一段時間。

分頁切回前景的行為屬於 `FE-R04`（`background-tab`），不是這裡。

### D5 —— 判準是「速率恆定」，不是「畫面看起來平滑」

用瀏覽器量抖動來當測試會 flaky（影格間隔本來就會變），而且它證明不了原因。

改成驗 M2 那條恆等式：**餵一串不穩定的 `dt`，斷言每一幀的
`(畫面位移 / dt)` 都等於 `MOVE_SPEED`。**

拿掉插值的話，同一組輸入會算出 0（那一幀沒走）或 8（走了兩步）——
**立刻紅，而且紅在正確的位置。**

這條不變量只在**沒有障礙物、方向不變**時成立。撞到牆時速率當然會變 ——
所以規格把界線寫進 Requirement，測試也在開闊處跑。

### D6 —— 純函式吃一個 step 回呼

要讓 D5 那個測試跑得起來，累加器 ＋ 插值那段必須在 R3F 之外可呼叫。
但它中間要真的推進物理（Rapier）。

所以抽出來的函式吃一個**回呼**：「跑一個固定步，回傳新位置」。
正式碼傳的是呼叫 Rapier character controller 的那個；
測試傳一個等速位移的。

**被替換掉的是「一步怎麼走」，不是「幾步、畫在哪」** ——
而後者正是會抖的那一半，測試打的就是它。

## 驗證方式

- **V1 速率恆定**：餵一串刻意不整除 `fixedStep` 的 `dt`
  （含比一步短、比一步長、剛好一步的），斷言每一幀的
  `畫面位移 / dt` 等於 `MOVE_SPEED`（允許浮點誤差）。
- **V2 突變測試（驗收條件）**：把插值換成「直接回傳目前的物理位置」，
  V1 必須變紅。
- **V3 靜止**：不按鍵時畫面位置**完全不動** —— 插值寫錯的話
  它會在停下來之後繼續朝 `cur` 漂過去。
- **V4 相機**：斷言相機的 target 拿到的是**畫面位置**，不是物理位置（D2）。
- **V5 網路**：斷言送出去的 pose 拿到的是**物理位置**，不是畫面位置。
  V4 與 V5 互為對照 —— 只寫一條的話，一個「兩邊都給同一個值」的實作會通過。

**測試連到什麼**：不適用 —— 這個 change 的測試不連任何外部服務。

## 這把尺量不到什麼

- **證明不了「畫面看起來不抖」。** 它證明的是速率恆定，而那是抖動的成因。
  兩者之間隔著瀏覽器的合成與顯示器 —— 那一段沒有機器在看。
- **不涵蓋撞牆時的觀感。** 撞牆那一瞬間速率本來就會變，
  這條不變量在那裡不成立，規格也明寫了界線。
- **不涵蓋 120 Hz 以上的螢幕。** 量測是在 60 Hz 下做的。
  恆等式與更新率無關，但那是推導不是量測。
