# `FE-W19` design

## 這一份要回答的

規格說「`av=1` 與 `av=0` SHALL 呈現一般遊戲視角下可清楚辨識的外觀差異」。
**那句話機器讀不懂。** 這一份把它變成一個量得出來的數字，
並且說明那個數字為什麼不是恆真的。

## M1：量測 —— 換一個部位的顏色，畫面上差多少

用真的 `three`（套件本體）＋ 真的 WebGL（Chromium/SwiftShader）渲染 `ChibiPlayer`
的同一組幾何。512×512，固定相機正對角色、固定光照、無動畫。
背景純黑，「角色像素」＝非背景像素 ＝ **59347**（佔畫面 22.64%）。

差異像素的定義：**RGB 任一通道絕對差 `≥ 32/255`**。

| 只換一個部位 | 差異像素 | 佔角色像素 |
|---|---|---|
| 皮膚（頭）`#f2c9a0` → `#a0c9f2` | 26426 | **44.53%** |
| 四肢 `#3b4794` → `#94873b` | 16232 | **27.35%** |
| 軀幹 `#4d5bb0` → `#b0a24d` | 14471 | **24.38%** |
| 眼睛 `#20232e` → `#e0ddd2` | 2203 | **3.71%** |
| 同色系換一階 `#4d5bb0` → `#5f6cc0` | 0 | **0.00%** |
| 對照：什麼都不換 | 0 | **0.00%** |

⚠️ **量測環境的誠實說明**：光照是為了量測設的（AmbientLight 1.6 ＋
DirectionalLight 2.0），相機正對角色且距離很近。真實遊戲畫面是俯視角、
角色小得多。**這些數字是相對量級的參考，不是正式場景的絕對值。**

### 這張表講了三件事

**第一，三個大面積部位全部在 24% 以上，眼睛是 3.71% —— 中間是空的。**
所以閾值不需要精確調校，只要落在那個斷層帶裡就行。

**第二，眼睛的 3.71% 恰好落在兩位審查者原本給的 3% 與 5% 中間。**
也就是說那兩個數字的差別不是理論問題，是「**只改眼睛算不算一種 avatar**」的
產品決定。兩邊看到數據之後都選了「不算」。

**第三（兩邊在看到數據之前都沒講到）：同色系換一階是 0.00%。**
`#4d5bb0` → `#5f6cc0` 三個通道分別差 18、17、16，**每一個都 `< 32`**。

第三點是這次量測最重要的產出：**`≥ 32/255` 這個門檻會默默變成對調色盤的限制**。
設計師拿同色系不同深淺做兩款 avatar，程式完全正確，測試會紅，
而規格上沒有任何一句話說過不可以。

**處置**：把它升級成規格明文（`FE-W19-S04`／`S05`），而不是留在測試的 magic number 裡。
codex 逐字：「量測方法可以驗證產品決定，不能自行創造調色盤限制。」

## D1：閾值 —— 通道差 `≥ 32/255`，差異像素 `≥ 10%`

**`32/255`**：足以排除抗鋸齒邊緣、光照取整與陰影造成的小幅色差。

**`10%`**：落在 3.71% 與 24.38% 的斷層帶中間。

- 往下：明確排除「只改眼睛」與「只改配件」這種不符合需求的實作。
- 往上：對最小的大面積部位（軀幹 24.38%）保留約 **2.4 倍**餘裕 ——
  真實場景的俯視角、角色尺寸、遮擋與抗鋸齒都會讓這個比例縮水，
  2.4 倍是為了不讓正確的實作偶發失敗。

**為什麼不是 15% 或 20%**：它們沒有增加任何語意區分（24.38% 以上都是同一類），
只是把偽陽性的風險往上推。

**兩種錯誤哪一種比較貴**：偽陰性（實作壞了但測試綠）。
因為它的症狀是「發表當天角色選擇沒有作用」，而那正是這一項存在的理由。
偽陽性只是讓我們多查一次。

## D2：值域外的 `av` —— 一律回到 `0`，SHALL NOT 取模

兩位審查者第一輪在這裡分歧：一邊主張 `abs(av) % N`，一邊主張固定 fallback。
**第二輪主張取模的一方明確撤回。**

撤回的理由（逐字）：

> 實測證明無效的顏色不會引發 Runtime Error，而是靜默渲染成白色實體。
> 如果使用取模，異常或惡意的 ID 會被「合法化」並悄悄對應到另一個有效角色，
> 這會掩蓋資料錯誤或後端漏洞。

另一邊補了一個內部矛盾：取模方案自己的判準要求 `-1` 與 `999` 都跟 `av=0` 像素相同，
但 `abs(-1) % 2` 與 `999 % 2` 都是 `1` —— **那個判準跟它自己的實作不相容。**

### 發表現場的具體後果

| | 陌生使用者看到什麼 |
|---|---|
| fallback 到 `0` | 預設角色。可能不是他預期的外觀，但**所有異常值都呈現同一個明確的降級結果** |
| `abs(av) % N` | 第二款角色，**看起來像系統成功載入了他選的角色**。沒有錯誤、沒有異常，而後端資料其實壞了 |

而且取模**會隨版本漂移** —— `N` 從 2 變成 4 的那天，同一個 `999` 會無故換一款角色。

## D3：`av=0` 是哪一款

`av=0` SHALL 是今天已經在畫面上的那一款（`skin` / `avatarBody` / `avatarLimb` / `ink`）。

**理由**：這一項不改變任何現有使用者看到的東西。今天所有人的 `av` 都是 0
（後端 `session.get("avatar_id") or 0`），所以把 `av=0` 定成現況等於
**這一項對現有畫面的淨變化是零**，而所有紅燈都只可能來自新加的那一款。

## 驗證方式

⚠️ **這一節不是「跑哪些測試」，是「憑什麼相信它真的做到了」。**

### V1 —— 本地：`av=0` 與 `av=1` 在真的 WebGL 上差得夠多

固定相機、光照、姿勢、畫布尺寸與取樣影格，分別渲染 `av=0` 與 `av=1`，
在 `requestAnimationFrame` 裡用 `gl.readPixels()` 讀 back buffer。

⚠️ **一定要讀 back buffer，不能用 `toDataURL()` 或截圖。**
畫布沒開 `preserveDrawingBuffer`，截圖取到的是全透明 ——
這個坑在 `FE-A06` 踩過一次，症狀是「3D 世界一片空白」而產品其實好好的。

判準：差異像素（任一通道 `≥ 32`）佔角色像素 **`≥ 10%`**。

### V2 —— 遠端：走完整條資料路徑

注入協定合法的 snapshot（同位置、同朝向，只有 `av` 不同），
讓它走 `snapshot → 遠端名單 → 遠端角色元件 → 畫面`，再用 V1 的判準。

⚠️ **不能直接對映射函式斷言。** `av` 早就在 `RemoteIdentity` 裡了，
而今天沒有任何地方讀它 —— **協定送得到不等於畫得出來**，
這一項存在的理由就是那個落差。

⚠️ **不依賴真實帳號的 `avatar_id`。** 今天沒有任何 UI 改得動它（那是 `FE-A05`），
所以「等真的有人選了再驗」等於永遠不驗。注入 snapshot 不是偽造使用者行為，
是驗證一個**已經存在的 WebSocket 消費端契約**。

### V3 —— 值域外的四個值

`-1`、`999`、`1.5`、`null` 逐一注入實際渲染入口，判準是「與 `av=0` 的畫面相同」。

⚠️ **V3 單獨存在時是恆真的。** 一個完全忽略 `av`、永遠畫預設的實作會讓
V3 全綠。所以 **V3 SHALL 與 V1 同時成立才算通過** —— 這是 `FE-W19-S10` 的用途。

`999` 那一條還要多一句：**SHALL NOT 與 `av=1` 相同**。少了它，取模的實作也會通過。

### V4 —— 顏色沒有離開 design token

檢查角色元件的原始碼裡沒有字面色碼。

## 突變條件

⚠️ **驗收條件不是「測試全綠」，是「把防禦拿掉，測試要變紅」。**

| 拿掉什麼 | 哪一條要變紅 |
|---|---|
| 角色元件不再讀 `av`（回到模組層級常數） | V1、V2 —— 差異變成 0.00% |
| 遠端角色不把 `av` 傳下去（只有本地讀） | **V2 單獨變紅，V1 仍綠** |
| 值域檢查換成 `abs(av) % N` | V3 的 `999` 那一條（它會變成 `av=1`） |
| 值域檢查整段拿掉 | V3 —— 角色變成白色方塊人（不會丟例外，所以只有像素判準攔得住） |
| 把差異改成只換眼睛 | V1 —— 3.71% < 10% |
| 在元件裡寫死色碼 | V4 |

⚠️ 第二列是這張表最重要的一列：它證明 V2 **不是** V1 的重複。
本地與遠端各有一條路徑，而「本地對了」推不出「遠端對了」。
