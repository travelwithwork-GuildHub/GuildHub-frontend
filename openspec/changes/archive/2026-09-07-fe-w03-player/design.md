## Context

動機見 `proposal.md`，需求見 `specs/`。四個既有條件：

1. **相機定案了**（`FE-W05`），所以「+Z 是畫面下方」有依據了 ——
   `FE-W02` 交接過來的那個驗證現在做才算數。
2. **`world-coordinates` 是唯一一份。** 朝向要 import，不得重寫。
3. **`CONTEXT.md`：高頻資料不進 React。** 位置、朝向、**動畫相位**
   都不得進 React state 或 Zustand。
4. **沒有碰撞。** `FE-W04` 才做 collider 與 World Bounds ——
   本次的角色會走出地板，那是刻意的。

## Goals / Non-Goals

**Goals:**

- 兌現 W1 里程碑的「走得動」
- 把 `FE-W02` 交接的視覺驗證做掉（**這是本項最重要的產出之一**）
- 輸入、移動、動畫都做成純函式，讓 jsdom 測得到核心邏輯

**Non-Goals（設計層面）:**

- 不決定角色長什麼樣（`FE-W08` ProceduralAvatar，W3）
- 不決定速度與動畫幅度的「手感」數值（視覺係數，見 D3）

## Decisions

### D1：輸入、移動、動畫全部拆成純函式

`FE-W01` 學到的教訓：3D 的東西在 jsdom 裡幾乎驗不到。
所以能抽成純函式的都抽出來 —— 這一項的**核心邏輯**（哪個鍵對哪個方向、
對角線會不會比較快、動畫相位連不連續）因此都測得到，
只剩「角色長什麼樣、走起來順不順」需要眼睛。

### D2：方向要正規化，而且要有測試

沒有正規化的話對角線快 41%。這是遊戲開發最常見的 bug 之一，
而且**看得出來但很少有人查得出來** —— 玩家只會覺得「斜著走比較快」。

`S05` 把它釘住。

### D3：速度與動畫幅度**不寫進 Requirement**

跟 `FE-W05` 的 `viewHeight` 同一類：它們是**手感／視覺係數**，
`FE-W08`（正式 Avatar）與 `FE-W14`（VisualPolish）會調。

Requirement 寫**性質**（有上限、對角線不更快、與影格率無關、相位連續），
暫定值放這裡：**移動速度 4 世界單位／秒**、
**Walk 週期 0.6 秒**、**bounce 幅度 0.06 世界單位**。

對照 `FE-W02` 的比例 32：那個是單位定義，有測試釘住。這幾個沒有。

### D4：朝向 import `world-coordinates`，不重寫

那份 design 的 R1 明寫「沒有機器擋得住複製」。這一項是第一個會用到它的地方，
所以**這裡建立慣例**：import，不重寫。
`tasks` 有一條驗收是 grep 確認沒有第二份判斷。

### D5：動畫相位用**累積的時間**，不用 `performance.now()`

相位 = 上一個相位 + dt × 速率。這樣：

- 它是純函式，測得到（`S12` 的連續性）
- Idle 與 Walk 切換時相位不重置，所以不會跳
- 分頁切到背景再回來時，dt 很大但相位只是往前走，不會錯亂

用 `performance.now()` 的話相位跟真實時間綁死，切換狀態時會跳，
而且測試要 mock 時間。

### D6：角色是 primitive 組的，**不載入任何外部模型**

`CONTEXT.md` 的詞彙表：Procedural Avatar 是「由 primitive
（RoundedBox / Capsule / Sphere）組出來的 Chibi 角色，**不是**載入外部模型」。

本次這隻是**簡單版**：頭、身體、兩隻手、兩隻腳，能看出朝向與走路。
`FE-W08` 會換成模組化的正式版（Head / Hair / Body / Arms / Legs）。

## 驗證方式

| Scenario | 怎麼證明 |
|---|---|
| `S01`–`S04` 輸入 | 單元測試（純函式） |
| `S05`–`S07` 移動與速度 | 單元測試（純函式） |
| `S08` `S09` 朝向 | 單元測試（純函式，且斷言它用的是 `world-coordinates`） |
| `S10`–`S12` 動畫 | 單元測試（純函式） |
| `S13` 相機 target 不觸發 re-render | 單元測試（渲染次數計數） |

### 人工瀏覽器驗證（production build）

**V1 是 `FE-W02` 交接過來的那件事，它是本項的完成條件之一。**

| # | 動作 | 要留的證據 |
|---|---|---|
| V1 | 按 **S／↓** | 截圖：**角色在畫面上往下走**。這是 `FE-W02` 的 R4 交接過來的 |
| V2 | 按 W／A／D | 截圖：分別往畫面上／左／右 |
| V3 | 斜著走（同時按兩個鍵） | 目視：不比直線明顯快 |
| V4 | 走一段路 | 截圖：相機平滑跟隨，角色不會跑出畫面 |
| V5 | 站著不動 | 目視：Idle 動畫在動，**角色沒有轉頭** |

**連到哪裡**：只連本機自己起的 production build。

### 自動化證明不到的

1. **角色好不好看、走起來順不順。** `FE-W08`／`FE-W14` 的事
2. **速度手感。** 4 單位／秒是暫定的，沒有測試釘住
3. **V1 的視覺對映。** 純函式證明得了「+Z → 朝向 0」，
   證明不了畫面上真的往下 —— 那正是 `FE-W02` 交接過來的原因

## Risks / Trade-offs

**R1｜角色會走出地板** → 本次沒有碰撞也沒有邊界（`FE-W04`）。
緩解：這是刻意的，寫在 Non-goals。**但人工驗證時要知道這不是 bug。**

**R2｜`FE-W02` 的交接如果沒做，錯誤會一路帶到遠端玩家** →
V1 是本項的完成條件。沒做的話，`FE-R07` 的遠端玩家會全部反向，
而所有單元測試都是綠的。
緩解：V1 列進 `tasks` 的驗收，證據貼在實作 PR 上。

**R3｜速度與動畫幅度沒有測試釘住** → 跟 `FE-W05` 的 `viewHeight` 一樣，
有人改掉不會有東西紅。緩解：刻意的（D3），註解寫明。

## Open Questions

- **速度、Walk 週期、bounce 幅度的最終值。** `FE-W08`／`FE-W14` 會定。
- **要不要有加速度／減速**（現在是瞬間到全速）。那會改變手感但不改變
  任何 Requirement，`FE-W04` 接上物理之後再看。
