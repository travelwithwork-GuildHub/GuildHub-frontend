# FE-R09 BrowserLoadTest —— 設計

## D1. 40 個真實瀏覽器不做，而這是量出來的不是推論的

```
開發機                                     8 GB
量測當下 swap                              已用 6.87 / 8 GB，可用實體記憶體 0.89 GB
一個 headless Chromium ＋ 空白 WebGL 頁面   225 MB
  1 個  260 MB      2 個  485 MB      3 個  692 MB      4 個  902 MB
```

每個瀏覽器約 225 MB，而那是**空白頁面** —— 真實場景還要加上 three.js 的場景圖、
Rapier 的 WASM 實例、WebSocket、shadow map 的 render target。

40 × 225 MB = 9 GB，**已經超過整台機器的實體記憶體**。

硬跑的結果不是「量到 40 人的效能」，是量到 macOS 的記憶體壓縮與 swap 行為 ——
那個數字跟我們的程式碼無關，而且會把機器鎖住。

**代價**：這一項的綠燈不涵蓋「40 個完整前端在同一台機器上」。
那件事要等硬體，或者換成多台機器 —— 規格要求把它寫進**輸出**（`S07`），
不是只寫在這裡。

## D2. 被測端是真瀏覽器，其他人可以是 WebSocket client

工作分解表寫著「**不是 WebSocket fake client**」。兩個模型獨立給了同一個解讀：
那句話是在防止把「40 人完整前端情境」偷換成「伺服器 socket 壓測」。

**被測的那一個瀏覽器仍然是真的**：它跑完整的前端，真的建立 39 個
`RemotePlayer`、真的每幀對每一個做插值、真的產生 draw call 與 shadow map。
被換掉的只有「其他 39 個人自己的前端」。

### 這把尺量不到什麼（規格 `S07` 要求寫進輸出）

- 40 個完整前端在同一台機器上的 CPU／RAM／GPU／VRAM 競爭
- 每個玩家自己的本地角色成本（輸入、物理、動畫、本地渲染）
- 多個瀏覽器搶同一顆 GPU 時，單一玩家的 FPS 衰退
- 真實客戶端的連線、重連、資源載入、WASM 初始化與 shader 編譯尖峰
- 不同客戶端之間的時鐘漂移與背景分頁節流

## D3. 假 client 不能送得太漂亮

Gemini 指出三個會讓結果偏樂觀的原因：

| | 為什麼會偏樂觀 |
|---|---|
| **節奏太完美** | 真實玩家有延遲突波與掉包。完美的到達節奏讓插值與位置修正的 CPU 峰值完全被掩蓋 |
| **同幀擁塞** | 真實情況下 39 個人的更新可能因為擁塞在同一幀抵達 —— 那一幀要反序列化並處理 39 個人的資料 |
| **移動太規律** | 一直線走跟走走停停、突然轉向的成本不同 |

所以假 client 的送出間隔要有抖動、要有一部分刻意擠在同一時間、移動要有變化。

**而且要能關掉**（`S04`）—— 關掉之後數字必須變好，否則代表那些特性
根本沒有進到被測瀏覽器，那時候 `S03` 是裝飾。

## D4. 網路基準與渲染預算分開量

**因為處置完全不同**：

```
伺服器／協定撐不住   →  改後端或協定
瀏覽器渲染撐不住     →  改渲染（FE-W13，W5）
```

混在一起量的話，一個壞掉的數字指不出要修哪一邊 —— 而這一項存在的理由
就是「給出一個能做決定的數字」。

網路基準**不開任何瀏覽器**，所以它跑得動 40 個（純 WebSocket client 很輕）。

## D5. 「畫面上真的有幾個人」用 three.js 自己的 devtools hook

`FE-R08` 的 E2E 已經有先例：`Scene` 的建構子會對 `window.__THREE_DEVTOOLS__`
送一個 `observe` 事件，用 `addInitScript` 先定義好就拿得到 Scene 物件。

**刻意不在正式碼開 debug 出口** —— 那種出口會一路活到正式站。

這個數字是 `S02` 的基礎：**畫面上人數對不上就失敗，不回報 FPS**。
沒有這一條的話，最容易發生的假綠燈是「39 個人根本沒出現，所以 FPS 很漂亮」。

## 待答問題（實作時量；量完如果動到 Requirement 就回來重開 spec PR）

- **Q1：N 要多少？** 從小往上爬，找出**這台機器上被測瀏覽器開始掉幀的人數**，
  以及**假 client 開始連不滿的人數**。兩個都要記錄 ——
  後者是工具的上限，不是產品的上限，混在一起會得出錯的結論
- **Q2：FPS 的判準是什麼？** 中位數、p99、還是「低於某個值的幀佔比」。
  `FE-R08` 的教訓是**判準本身會被環境污染**（SwiftShader 的幀間隔抖動
  讓同一份程式碼五次量到 2.05–3.62）。要先看分佈再決定，不要先訂數字
- **Q3：FPS 怎麼取得？** rAF 計數最直接但會被自己影響；CDP 的
  `Performance.getMetrics` 是另一條路。要量哪一個比較穩
- **Q4：假 client 用什麼寫？** Node 內建的 WebSocket（Node 24 有）可以避免
  多一個相依。要確認它撐得住幾十條連線
