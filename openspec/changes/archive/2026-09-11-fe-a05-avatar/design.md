# `FE-A05` design

## D1 `N = 2`，不是「先做幾款再說」

兩個審查者獨立給了同一個數字，理由也一樣：**這一列的價值是閉環，不是角色庫。**

多做一款不只是多配幾個顏色，它會同時增加：本地與遠端映射的一致性成本、
每款外觀的瀏覽器像素判準、選擇器版面與辨識性驗證、值域與 fallback 的相容性。
在 8 點內多做款式，**最可能排擠掉真正困難的那一半**（讓別人看見）。

規格寫「恰好兩個」而不是「至少兩個」，是為了不把 `N` 留成一個未決的 magic number。

## D2 預覽 = 直接改世界裡的自己

三個選項都被評估過：

| | 做法 | 為什麼不 |
|---|---|---|
| (a) | 第二個 Canvas 做 3D 預覽 | 額外的 WebGL context、相機、燈光與效能問題 |
| (b) | 靜態縮圖／色塊 | **兩套呈現會漂** —— 「選的時候像 A、進去像 B」比沒有預覽更糟；而且縮圖只證明顏色選中了，不證明角色在世界裡真的長那樣 |
| **(c)** | **直接改世界裡的自己** | 重用既有元件與既有 Canvas，成本最低，而且預覽的就是實際渲染 |

⚠️ **(c) 帶來一個 (a)/(b) 沒有的責任：預覽與已儲存值必須分得開。**
規格的 `S02`（別人看不到未提交的選擇）與 `S03`（放棄要復原）就是為此。

## M1 為什麼「PATCH 成功」不等於「別人看得到」

⚠️ **這是實測的事實，不是推測。**

即時層每個人的 `av` 來自**那條 WebSocket 連線背後的 session**，
而 `avatar_id` 是後端在 `auth.py` 的 `_remember()`（**登入時**）寫進 session 的；
`presence.join()` 從 session 讀它。

所以 `PATCH /api/profiles/me` 成功之後，**那條已經建立的連線背後的 session
不會更新** —— 已經在場的其他人看到的仍然是舊外觀。

**這正是 `docs/WBS.md` 警告的那件事**：

> 使用者選完之後自己的外觀不變、**別人看到的他也不變**，
> 那是製造錯誤期待不是 MVP

## D3 靠重新建立連線，並且承認它的代價

三個選項：

| | 做法 | 判定 |
|---|---|---|
| (a) | **`PATCH` 成功後主動重新建立即時連線** | **採用** |
| (b) | 只保證自己看得到，別人下次看到 | **出局** —— 直接違反這一列的前置條件 |
| (c) | 開後端票要求 `PATCH` 也更新 session，這一列先擋著 | **出局** —— 前端有辦法自己完成閉環，而這個專案的原則是沒有任何一項在等後端 |

⚠️ **(a) 的代價是真的，所以它進了規格而不是註解**（`S05`）：
重連期間其他人可能短暫看到這個人離開又進來。

⚠️ **失敗語意是這個決定的一半**（`S06`／`S07`）：

- `PATCH` 失敗 → **不重連**。重連有代價，為一次失敗的儲存付它毫無所得；
  而且重連之後別人看到的還是舊外觀，畫面會像「改了但沒改成」。
- 重連失敗 → **不宣稱「其他人已經看到」**，但選擇仍然是已儲存的
  （下次連線就會生效）。

後端票：`PATCH` 時同步 session。做了就能消除 `S05` 那個現象。

## D4 `0` 是 falsy，而這件事會靜默地吃掉第一個角色

⚠️ **這是這一份裡最具體的實作陷阱**，所以它有自己的 Scenario（`S08`）。

`ProfileUpdate` 的每一欄都是選填（未給的欄位不動），所以很自然會寫成
「有值才帶上這個欄位」。而**索引 `0` 是 falsy** ——
使用者選第一個角色時，那樣的實作會**什麼都不送**。

症狀最惡劣的地方在於：**預覽是對的**（本地狀態確實改了），
所以畫面上看起來完全正常，只有重新整理之後才會發現沒存到。

⚠️ 另外 `avatar_id` 送 `null` 會**清空**欄位，而 `ProfileOut.avatar_id`
是必填的 `number` —— MVP 沒有「無角色」狀態，所以規格寫 SHALL NOT（`S09`）。

## D5 入口只在 `/world`，而 WBS 的敘述要改

`docs/WBS.md` 要求這一列「接手 `FE-A06` 的角色選擇那一段」，
但**首次進入流程在 `/`，那一頁沒有 3D Canvas**。

兩個審查者獨立選了「只放在 `/world`」，而且都主動說了同一句話：
**要在 WBS 上明寫這一列沒有接手那一段，不應該假裝完成了原範圍。**

## D6 常駐入口，不做一次性提示

| | 做法 | 判定 |
|---|---|---|
| **(1)** | **一直都在的入口** | **採用** —— 零狀態負擔 |
| (2) | 首次進入世界的一次性提示 | 出局 —— 「一次性」要記住「看過了」（額外的持久狀態），而且提示關掉之後「入口在哪」原封不動 |
| (3) | 什麼都不做，留給 `FE-A04` | 出局（見下） |

⚠️ **(3) 一開始有一位審查者支持，理由是範圍蔓延。**
把這個專案的歷史交給他之後他改口了 —— 而那個歷史是：
**同一天踩了兩次「做了但使用者看不出來」，兩次都測試全綠。**

- `world-interactive-objects`：六扇門是 10 像素的細縫，**444 條測試沒抓到**
- `control-affordance`：按鈕是漂著的字、輸入框隱形，**18 條端到端斷言全綠**，
  使用者傳截圖來罵才發現

**選擇器做好了而沒有人找得到入口，就是第三次。**

## ⚠️ 已知缺口：可發現性沒有自動判準

規格量得到的是「入口夠大、夠亮、沒被蓋住、不用操作就在那裡」
（`S11`／`S12`／`S13`，對比度沿用 `control-affordance` 的 `3:1`）。

**量不到的是「使用者知道那顆按鈕是幹嘛的」。**

兩個審查者被直接問到這一點，**兩邊都答「沒有」，而且都明確拒絕編一個**。
這個缺口寫進了規格本身 —— 留白或塞一句「SHALL 清楚可見」，
都會讓下一個人以為它被守住了。

## V 驗證

- **V1** 選取之後，世界裡的自己換了外觀（`S01`）——**要在真的 Canvas 上量像素**，
  沿用 `avatar-appearance` 的保守差異（多幀交集）
- **V2** 未儲存的選擇不會出現在別人的畫面上（`S02`）
- **V3** 放棄之後預覽復原（`S03`）
- **V4** 儲存成功後，**先前就在場**的另一個瀏覽器看到新外觀（`S04`）
  —— 這一條要兩個真的瀏覽器
- **V5** 儲存失敗不重連（`S06`）；重連失敗不宣稱生效（`S07`）
- **V6** 選第一個角色時送出的是 `avatar_id: 0`（`S08`）
- **V7** 任何路徑都不送 `null`（`S09`）；值域外不送出（`S10`）
- **V8** 入口不需操作就可見、有面積、對比 `≥ 3:1`、不被畫布蓋住（`S11`–`S13`）

### 突變（驗收條件）

⚠️ **不是「測試全綠」，是「把防禦拿掉，測試要變紅」。**

- **X1** 選取只改待存值、不改世界裡的自己 → V1 要紅
- **X2** 預覽直接寫進送給別人的狀態 → V2 要紅
- **X3** 儲存成功後**不重連** → V4 要紅、V1 要仍然綠
      （這一條證明 V4 不是 V1 的重複，也是這一列的核心）
- **X4** 儲存失敗也重連 → V5 要紅
- **X5** 用「有值才帶欄位」送 `PATCH` → **V6 要紅**（`0` 被吃掉）
- **X6** 拿掉值域檢查 → V7 要紅
- **X7** 入口改成一次性提示（預設關閉）→ V8 要紅
- **X8** 入口的 `z-index` 拿掉 → `S13` 要紅
      （⚠️ 只有真瀏覽器抓得到，jsdom 沒有堆疊脈絡）
