## Context

動機見 `proposal.md`，需求見 `specs/`。四個形塑做法的既有條件：

1. **`FE-W01` 的相機是暫時的。** `camera={{ position: [4,4,4], fov: 50 }}`
   是 perspective，而 `CONTEXT.md` 訂的是 Orthographic。
2. **`FE-W02` 的視覺契約靠這一項成立。** 那份規格定了「+X 畫面右、+Z 畫面下」，
   但那件事**由相機決定**。現在只是巧合。
3. **`CONTEXT.md`：高頻資料不進 React。** position / rotation / 動畫相位
   不得寫入 React state 或 Zustand。違反這條不會有錯誤訊息，只會變慢。
4. **現在沒有東西可以跟隨。** 角色是 `FE-W03`。

## Goals / Non-Goals

**Goals:**

- 把 `FE-W02` 的對映從「巧合」變成「有依據」
- 讓 `FE-W03` 交接過來的視覺驗證有一個定案的基準
- 平滑做成純函式，**這一項的核心邏輯不需要瀏覽器就測得到**

**Non-Goals（設計層面）:**

- 不決定構圖的美感（`FE-W14` VisualPolish，W5）
- 不決定 Guild Hall 在這個相機下怎麼配置（`FE-W11`，W3）

## Decisions

### D1：target 用 **ref**，不是 prop 值

`CONTEXT.md` 的硬規則。`FE-W03` 的角色會每幀移動 —— target 若是普通的
React prop，每幀都會觸發整棵樹重新渲染。

**這條寫進 Requirement 而不只是註解**，因為它的違反是無聲的：
畫面照樣對，只是慢，而且慢的原因在別的地方看不出來。
`FE-W05-S08` 用「渲染次數不增加」把它變成可測的。

### D2：平滑用**半衰期**，不是每幀固定係數

常見的寫法是 `pos += (target - pos) * 0.1`。那個 `0.1` 是**每幀**的比例，
所以在 120 Hz 的機器上會比 60 Hz 快一倍 —— 而且沒有任何東西會告訴你。

改成與時間有關的衰減：

```
pos += (target - pos) * (1 - 2 ** (-dt / halfLife))
```

半衰期的好處是它**可以被純函式測試釘死**：經過一個半衰期，
剩餘距離剛好減半；同一段時間拆成幾次更新，結果相同（`S05`）。

極大的 `dt`（分頁切回前景）不需要特別處理：`2 ** (-∞)` 趨近 0，
所以係數趨近 1，相機收斂到 target 而不會越過它。這是這個公式自帶的性質，
不是額外加的保護 —— 但仍然要有 Scenario 釘住（`S06`），
因為換一個公式的話它就不成立了。

### D3：相機方位 = target + (0, H, D)，H > 0、D > 0

看向 target。這個擺法讓 **+X 出現在畫面右、+Z 出現在畫面下** ——
`FE-W02` 那份對映的視覺依據。

**規格只約束方位的性質，不約束 H 與 D 的值**（見 D4）。
用投影驗證（`S02`）而不是斷言座標：性質才是要保護的東西。

### D4：垂直可見高度與半衰期**不寫進 Requirement**

`config.yaml` 有兩條規則在這裡打架：

- specs：「數值限制與預設值要寫進 Requirement 本身」
- design：「**還不知道答案的常數**不要寫進 Requirement⋯⋯threshold、**係數**
  這種要靠實作量出來的東西，列成 design 的待答問題」

這兩個數字適用後者：它們是**視覺選擇**，`FE-W14` VisualPolish 明文會調
（「固定 Camera 下的構圖與可讀性」）。寫死在 Requirement 的話，
`FE-W14` 調整時就得回來打破 `FE-W05` 的規格與測試。

**對照 `FE-W02` 的比例 32**：那個不是視覺選擇，是**單位定義** ——
沒有待發現的正確值，任何值都對只要所有人用同一個。兩者不同類。

所以 Requirement 寫**行為**（垂直範圍固定、以半衰期衰減），
暫定值放這裡，測試用參數驗純函式的衰減邏輯而不綁死那個數字。

暫定值：**垂直可見高度 20 世界單位、半衰期 0.12 秒**。

### D5：構圖驗證用 three.js 的相機數學，不用瀏覽器

`camera.updateMatrixWorld()` 之後 `vector.project(camera)` 給出 NDC 座標 ——
**那是純數學，不需要 WebGL、不需要 canvas**。所以 `S02`、`S09`、`S10`
全部是單元測試。

這一項跟 `FE-W01` 不同：那一項有一半只有眼睛驗得了，這一項幾乎都測得到。

## 驗證方式

| Scenario | 怎麼證明 |
|---|---|
| `S01` 投影型別 | 單元測試（檢查相機型別） |
| `S02` +X 右、+Z 下 | 單元測試（`vector.project(camera)` 的 NDC 座標） |
| `S03` 沒有旋轉操作 | 單元測試（渲染後沒有相機控制的事件監聽） |
| `S04`–`S07` 平滑 | 單元測試（純函式） |
| `S08` target 不觸發 re-render | 單元測試（渲染次數計數） |
| `S09` `S10` 構圖 | 單元測試（相機數學） |

### 自動化證明不到的

**「這個俯視角看起來對不對」證明不了。** 單元測試證明得了 +Z 在畫面下方，
證明不了那個角度好不好看、遮擋多不多、角色會不會被家具擋住 ——
那是 `FE-W14`（VisualPolish）與 `FE-W11`（Guild Hall 構圖驗證）的事。

**一次人工確認**：起 production build 看 `/world`，確認畫面是俯視、
方塊沒有透視變形（orthographic 的特徵：平行線保持平行）。留截圖。

## Risks / Trade-offs

**R1｜暫定值會被當成定案** → `20` 與 `0.12` 只在 `design.md` 與程式碼常數裡，
沒有測試釘住。有人改掉不會有東西紅。
緩解：這是刻意的（D4）。程式碼註解寫明「暫定，`FE-W14` 會調」。
**代價是這兩個數字沒有保護** —— 接受，因為釘住它們的代價更大。

**R2｜`S03`「沒有旋轉操作」很難證明不存在** → 測試只能斷言
「我們沒有掛 OrbitControls 之類的東西」，不能證明未來不會有人加。
緩解：Requirement 用 MUST NOT 寫清楚；真正擋得住的是 review。

**R3｜`FE-W03` 接上真的角色之後，平滑的手感可能不對** →
本項的 target 是靜止的，`S04`–`S06` 驗的是數學性質不是手感。
緩解：`FE-W03` 的完成條件包含手感確認；半衰期是暫定值，那時可以調。

## Open Questions

- **垂直可見高度與半衰期的最終值。** `FE-W14` 會定（D4）。
- **相機要不要有前瞻（look-ahead）** —— 角色移動時相機稍微往前帶。
  那會改變手感但不改變任何 Requirement，`FE-W03` 做完再看。
