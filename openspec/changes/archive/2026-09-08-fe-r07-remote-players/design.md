## Goals / Non-Goals

範圍見 `proposal.md`〈不做什麼〉。

**Goals**
- 讓「看得到別人」在這一刀成立。
- 讓分層在**型別上**就分得開，而不是靠紀律。

**Non-Goals**
- 不做插值、不做朝向轉場、不做資源釋放的量測。

## Decisions

### D1. 兩個容器，不是一個 store 加一個「不要用 setState」的約定

名單與動態的**生命週期不同、頻率差三個數量級**，所以是兩份東西：

```
roster    Map<id, {name, av}>       React state。join / leave 才動
motion    Map<id, {x, y, f}> 的 ref  每秒 400 次。不進 React
```

考慮過「一個 store，位置那幾個欄位約定不要觸發重繪」—— 否決：
那條約定沒有任何東西在擋，而違反它**不會有錯誤訊息，只會變慢**。
分成兩個容器之後，「把座標寫進 React」需要有人**刻意**去改型別。

### D2. 座標在寫入時換算，不在 render loop 換算

協定是整數像素，Three 要世界座標。換算放在收到訊息的那一刻，
不是每一幀。`world-coordinates` 已經有那個對映，**不在這裡重寫**。

理由是次數：訊息每秒 400 次，render loop 每秒 60 次 × 40 個角色 ＝ 2400 次。
換算放錯邊是六倍的工作量，而且它會**每一幀重算一個不會變的值**。

### D3. 父層統一收訊息，子元件只讀

**不要讓每個遠端角色各自訂閱 WebSocket 或 store。** 40 個訂閱者
在每則 `pos` 上都會被喚醒一次，而其中 39 個跟自己無關。

父層收訊息、更新兩個容器；子元件只拿一個穩定的 `id`，
在 render loop 裡讀自己那一份。

### D4. 40 個 React 元件，不用 InstancedMesh

兩位審查者獨立給了同一個答案：**現在不要 instancing**。

- 40 個 group 加少量 primitive 對 WebGL 不構成負擔。真正貴的是
  「每則 `pos` 重繪 40 個角色」，而 D1 已經擋掉那件事。
- `ChibiPlayer` 是多個 primitive 組成的樹狀結構，有獨立的肢體與離散朝向。
  改成 instancing 是另一個大型渲染架構工作，不是這一刀的優化。

**這個決定有一個會失效的條件**：人數級距。40 人是 `FE-R09` 的 gate，
真的長到幾百人時要重看。那時的證據會是 `FE-O12` 的效能預算。

### D5. `removeRemote(id)` 是一個原子操作

`leave` 要清兩個容器。之後 `FE-R08` 會加 interpolation buffer、
`FE-R10` 會加狀態文字 —— 每加一份就多一個「忘了清」的地方。

所以清理收斂成單一個函式。**新增的每一份狀態都要加進那個函式裡**，
這件事寫在它的註解上。

## Risks / Trade-offs

- **「動態不進 React」沒有機器在擋** → 型別上分成兩個容器讓它需要刻意去破，
  但擋不住決心。緩解是 review 加上 `FE-R07-S01`（那條驗「名單物件沒有被換掉」）。
- **這一刀的角色會跳格** → 已寫進 Requirement，不是缺陷。
  但**使用者第一次看到會覺得壞了** —— PR 上要講清楚。
- **`name` 與 `av` 現在是常數** → 名單裡照收，但不要照著它們設計功能。
  `BE-G02`（每個人都是「訪客」）與 `BE-G03`（`av` 一律 0）都在等後端。
- **R3F 的自動 dispose 不是萬用的** → 共用的 geometry／material、
  或手動 `new` 出來的東西不會自動回收。這一刀不處理那件事，
  `FE-W07`（資源生命週期）才是。**但如果 `ChibiPlayer` 每個實例都各自
  建一組材質，40 人就是 40 組** —— 那個觀察要記在 `FE-W07` 的輸入裡。
