## Context

動機見 `proposal.md`〈Why〉。這裡只放量測與會影響取捨的現況。

**量到的事**（Node 的 WebSocket 連自己 `bash run.sh` 起的後端）：

| # | 事實 | 影響 |
|---|---|---|
| 1 | 端點 `/ws`，`scene` 預設 `lobby`，另有 `token` | D1 |
| 2 | 握手成功後 **`hello` 與 `snapshot` 相隔 <1ms** 一起到 | D2 —— 監聽器的安裝時機是正確性問題 |
| 3 | **`snapshot` 裡包含自己**（`players[0].id` 就是 `hello.you`） | 少了 id 會建出自己的分身 |
| 4 | 握手被拒 → `close code=1006`、`reason=""`、`wasClean=false`；**三種不同的失敗事件序列一模一樣** | D3 |
| 5 | 靜止 35 秒 `readyState=1`，期間 **0 則**應用層訊息 | D4 |
| 6 | 不需要登入；沒有 session 時後端**每次連線發一個新的 uuid4** | D5 |
| 7 | 一條連線只屬於一個 scene，沒有 switch 訊息 | D1 |

事實 4 的來源在後端原始碼的註解裡：「尚未 accept，`close()` 會讓握手直接以
**HTTP 403** 收場」。所以 `docs/WBS.md` 與 `CONTEXT.md` 寫的「close 1008」
**是伺服器端的動作，不是客戶端觀察得到的東西**。

## Goals / Non-Goals

範圍邊界見 `proposal.md`〈不做什麼〉。設計層級再補：

**Goals**
- 讓「什麼時候知道自己是誰」變成一個明確的狀態，下游不必自己猜。
- 讓**客戶端說不出口的事**（失敗原因）在型別上就說不出口。

**Non-Goals**
- 不做重連。`FE-R12`（W5）會在這一層外面包，所以這一層要**可以被包**：
  關閉是終態、清理是完整的、狀態轉移不可逆。
- 不做訊息分派。這一層把非 `hello` 的訊息原樣交出去，由 `FE-R02` 接。

## Decisions

### D1. `scene` 與 `token` 是連線參數，不是可切換的狀態

協定沒有 switch 訊息（事實 7），所以「換 scene」在型別上就是「關掉、重開」。

**不提供 `switchScene()` 這種會讓人誤會的 API。** 提供的是
「關閉現在這條、用新參數建一條」——名字要讓人看得出來會斷線。

考慮過在同一個 client 物件內部自動處理關閉重開 —— 保留這個做法，
但**規格要求舊連線先清理完成**：兩條同時存在的話後端會當成兩個人，
位置互相覆寫（那是 `FE-R06` 未定義的行為，不要在這裡意外觸發它）。

### D2. 監聽器在同一個同步區塊裡掛好

事實 2 是這條的全部理由：`hello` 與 `snapshot` 相隔不到 1 毫秒。
`new WebSocket(...)` 之後如果有任何 `await`、`Promise.then`、`setTimeout`
才掛監聽器，就可能漏掉 `hello`。

**這個 bug 是機率性的**，本機幾乎不會發生（本機 RTT 低到監聽器來得及掛），
在慢一點的網路上也不會發生（訊息更晚到）—— 它會在**恰好那個時間差**出現，
也就是最難重現的那一種。所以規格把它寫成明文要求，測試用一個
「建立後立刻在同一批送兩則」的替身 WebSocket 釘住。

### D3. 關閉交出事實，不交出原因；型別上不給分類的位置

事實 4 表示這幾種失敗**在客戶端無法區分**：

```
不合法的 scene      close 1006  reason=""  wasClean=false
room 沒帶 token     close 1006  reason=""  wasClean=false
路徑根本不存在      close 1006  reason=""  wasClean=false
後端沒有起來        （同上）
```

兩位審查者對這一點的處置不同：一位主張**把 code 整個抹掉**、只給一個
`ConnectionFailed`；另一位主張**留下原始事實但不承諾分類**。

**選後者**，理由是抹掉會毀掉診斷資訊 —— 在 DevTools 前面除錯的人需要那個碼，
而 `FE-R12` 的退避策略也需要 `opened`。**真正的風險是「承諾」不是「資料」**：

```ts
interface ConnectionClosed {
  code: number
  reason: string
  wasClean: boolean
  /** 這條連線的 open 事件有沒有觸發過。**這是客戶端唯一分辨得出來的事。** */
  opened: boolean
}
```

**型別裡沒有 `reason: 'bad-token' | 'bad-scene' | ...` 這種欄位，
而且不要加。** 加了之後，`FE-R12` 的人會寫出一段永遠不會執行的分支
—— 就像 `if (code === 1008)`（文件寫的那個碼客戶端看不到）。

### D4. 保活是一條否定契約，測試分兩層

事實 5 說應用層不用做任何事。但「不需要做」要怎麼證明？

**兩層，而且要說清楚各自證明了什麼**：

- **CI 跑的單元測試**：用替身 WebSocket 與 fake timer，進入 `ready` 之後
  把時間推進超過 35 秒，斷言 `send()` **一次都沒有被呼叫**、沒有為保活而設的計時器。
  **這一層證明的是「我們沒有加 heartbeat」** —— 有人之後加了它會紅。
- **不進 CI 的整合驗證**：連自己起的後端，靜止 35 秒，斷言
  `readyState === OPEN`。**這一層證明的是「伺服器那邊的保活真的有效」**，
  而它需要一份跑著的後端 —— `AGENTS.md` 寫 CI 不提供任何服務。

**不要用第一層冒充第二層。** 單元測試裡沒有真的 WebSocket，
它對「連線會不會被伺服器切掉」一無所知。

### D5. 這一層不宣稱 cookie 有沒有送到

事實 6：沒有 session 時後端每次連線發一個新的 uuid4，**所以漏帶 cookie
不會失敗，會安靜地變成另一個人**。

`FE-O09` 把「cookie 到底有沒有送到」留給這一刀。但**它需要瀏覽器** ——
Node 的 WebSocket 不帶 cookie，jsdom 也沒有真的 WebSocket。
所以這件事由〈驗證方式〉的 V2 用瀏覽器做一次，**不是單元測試**。

## 驗證方式

這個 repo 沒有成文的瀏覽器驗證規範，所以這一刀自己定義，並在 PR 上貼證據。

| # | 驗什麼 | 怎麼做 | 為什麼不能用單元測試 |
|---|---|---|---|
| V1 | 靜止 35 秒連線不斷 | 起後端，連上，靜止 35 秒後看 `readyState` | 單元測試沒有真的 WebSocket |
| V2 | 同一個瀏覽器分頁重連兩次，`hello.you` **一樣** | 瀏覽器開 `/world`，連兩次，比對兩次的 `you` | Node 不帶 cookie；這條要證明的正是 cookie 有送到 |
| V3 | 握手被拒時客戶端看到什麼 | 用不合法的 scene 連一次，記下 `code`／`reason`／`wasClean` | 已經量過一次（1006／空／false），這裡是回歸 |

**V2 目前預期會失敗**：現在還沒有登入（`FE-A01` 在 W2），
沒有 session cookie 就沒有穩定身分。**要把那個結果照實貼出來**，
並註明它由 `FE-A01` 之後補驗 —— 不要因為「還沒做登入」就跳過這條，
那會讓「cookie 有沒有送到」永遠沒有人驗。

## Risks / Trade-offs

- **`opened` 會被當成原因分類用** → 型別上擋不住。緩解是欄位註解與規格明文。
  **它只說「握手成功過沒有」，不說為什麼失敗。**
- **替身 WebSocket 跟真的行為不一樣** → 一定會有落差。緩解是 V1／V3 的整合驗證，
  以及**不要在替身上模擬我們沒量過的行為**。
- **這一層無法證明 cookie 有送到** → 已在 D5 與 V2 寫明，而且 V2 現在會失敗。
- **`FE-R02` 還不存在，非 `hello` 的訊息交出去之後沒有人接** → 刻意的。
  這一刀交出去就算完成，接的人是下一刀。規格明文寫「原樣交出」而不是「處理」。

## Open Questions

- 換 scene 時，舊連線的關閉要不要等到 `close` 事件真的觸發才建新的？
  等的話換場景會多一個 RTT 的延遲；不等的話有一小段兩條連線並存。
  **這不影響本 change 的形狀** —— 規格要求的是「舊的清理完成」，
  實作時量一次再決定，量到的數字寫進 PR。
