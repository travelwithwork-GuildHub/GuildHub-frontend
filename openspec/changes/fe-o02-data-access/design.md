# FE-O02 資料存取介面 —— 設計

## D1. adapter 的值叫 `internal`，不叫 `local`

`src/config/env.ts` 已經有一個 `NEXT_PUBLIC_APP_ENV`，值是
`local | preview | production`，意思是**部署目標**。它的 `local` 是
「跑在開發者的機器上」，而那時候連的是 `localhost:8000` 的**真後端**。

adapter 的 `local`（工作分解表的用字）意思相反：連我們自己的 Route Handlers。

**兩個 `local` 是相反的資料來源。** 兩個模型都說要換字。
選 `internal`，因為它跟 `guildhub` 形成的對比是「我們自己的／外部的」。

**代價**：跟 `docs/WBS.md` 的用字不一致。那一列要跟著改（另開 `chore/`），
而不是讓兩邊漂。

## D2. `internal` adapter 今天就存在，但每個操作明確失敗

三個選項：

| | 好 | 壞 |
|---|---|---|
| A. 不提供 `internal` | 少寫程式 | **切換邏輯變成一段永遠只走一邊的程式碼** —— 沒有第二條路，那 5 點就沒有東西可以驗 |
| B. `internal` 回假資料 | 畫面先做得下去 | 假資料會讓測試變綠而測不到任何東西；而且它是拋棄式的工作 |
| **C. `internal` 每個操作拋「尚未實作」（選這個）** | 切換邏輯有第二條路可驗；失敗是明顯的 | 在 `FE-O03` 做完之前，切到 `internal` 什麼都不能用（但那本來就是事實） |

錯誤訊息要帶三樣東西：**哪一個操作、哪一個 adapter、哪一個工作項目會補上它**。

**而且不得送出任何網路請求。** 只驗「有拋錯」的話，一個
「先送出去、失敗了再拋錯」的實作也會通過 —— 那會在 `internal` 模式下
偷偷打到真後端。

## D3. 回應用 Zod 的預設行為驗（strip），不用 `strict`

| 變更 | 應該怎樣 |
|---|---|
| 後端**新增**欄位 | **通過。** 那是相容的變更；讓它掛掉的話後端每加一個欄位都得等前端 |
| 後端**移除**必填欄位 | **立刻炸。** 讓它流下去的話，症狀是深層元件的 `undefined is not an object` |
| 後端**改型別** | 立刻炸。同上 |

Zod 的 `z.object()` 預設就是 strip（未知的鍵被丟掉，不報錯），
所以這一條不需要額外做什麼 —— **但需要一條測試釘住它**，
否則哪天有人「順手」加上 `.strict()`，後端加一個欄位就會讓整個前端掛掉。

失敗時拋一個可辨識的契約漂移錯誤，帶操作名與 Zod 的 issue。

**這不是 `FE-O01` 的型別漂移哨兵。** 那一個是 `tsc` 時期的、而且會過期
（比對的是上次 `contract:generate` 的結果）。這一個是**執行期**的。

## D4. 後端沒有的四個 domain 留白，而且用機械檢查擋住

`rest.ts` 已經立了先例：「Role / Application / Invitation / Offer 後端沒有
（`BE-G10`），刻意不出現在這裡 —— 它們由各自的工作項目在自己那一週加進來。」

這一層照做。但光靠註解擋不住 —— 所以加一條檢查：
`src/api/` 底下出現那四個 domain 的操作、而契約層仍然沒有對應 schema 時，紅。

**兩個方向都要顧**（`S09` 與 `S10`）。只擋不放的話，後端補上之後這條規則
會變成純粹的阻礙，而下一個人的選擇是把它整條刪掉 ——
**一條被刪掉的規則比一條寬鬆的規則糟。**

> codex 對這一條有保留：「呼叫點 import 直接紅未必是最佳工程狀態，會阻斷整個前端。」
> 那個顧慮在「已經有 UI 需要它」時成立 —— **今天沒有**（那四個 domain
> 的 UI 分別在 W6／W8／W9）。所以留白，並在那時候由各自的工作項目補。

## D5. 測試起一個微型 HTTP server，而它的 handler 拿同一份契約去驗

**不能用假的 `fetch`。** 這個 repo 有一條明確的教訓：在測試檔裡重刻一份
再斷言它，等於沒測。手刻的 `fetch` mock 就是那件事的另一個形式 ——
斷言「送出的 body 長這樣」時，那個「這樣」是我自己寫的第二份形狀。

做法：測試在 `127.0.0.1` 起一個微型 server（Node 內建 `http`），
**它的 handler 不自己寫死斷言，直接拿 `src/api/contract/` 的 schema
去 `safeParse` 收到的 request**。adapter 送錯就回 400，測試就紅。

### codex 指出這個做法還有四個洞，都要補

1. **契約自己寫錯的話，client 與 server 會一起通過。** 這個做法驗的是
   「adapter 遵守契約」，不是「契約等於凍結的真後端」—— 後者是
   `FE-O01` 的漂移哨兵與 `FE-O05` 的契約測試（W2）
2. **只 parse body 不夠。** method、路徑、query、必要的 headers
   （尤其 `credentials`）都要驗
3. **只測成功路徑的話，拿掉防禦不會紅。** 回應解析、錯誤轉譯、adapter 選路
   **每一個都要有自己的壞回應／壞設定測試**
4. **server 回的 response 不能隨手寫一個物件。** 要用同一份 response schema
   產生或先 parse 過；另外做「故意違約的回應」來確認契約漂移錯誤真的會拋

## 待答問題（實作時決定；動到 Requirement 就回來重開 spec PR）

- **Q1：操作的形狀是一個物件還是一組具名函式？**
  `api.profile.get()` 還是 `getProfile()`。判準是「呼叫點讀起來」與
  「tree-shaking 拿不拿得掉沒用到的」——**要量 bundle 才知道**
- **Q2：測試 server 的 port 怎麼選？** 固定 port 會在 CI 上撞；
  取 0 讓作業系統給的話要把實際 port 傳回設定。先量會不會撞
- **Q3：`credentials: 'include'` 在測試 server 上驗得到嗎？**
  jsdom 的 fetch 會不會真的帶 cookie 是要量的 —— 量不到的話，
  這條防禦要換一種驗法（例如驗傳給 `fetch` 的 init），並在規格上記明白
