# 0011. 阻斷式面板一次只開一個，由一個協調者持有

- **Status**: Proposed
- **Date**: 2026-09-18
- **Deciders**: fergus（規格 PR 雙審：codex、Gemini）
- **邊界狀態**: 僅約定（實作合併後改「已強制」，證據補 `tests/dom-visual-flow.test.tsx`）
- **證據**: `openspec/changes/fe-x16-dom-visual-and-flow/specs/dom-visual-system/spec.md` 的「同一時間只有一個阻斷式面板」

## 背景

看板、收件匣、我的名片各有自己的 provider，彼此不知道對方開著。截圖上訪客提示、看板、聊天框三個同時疊在畫面上，
使用者的原話是「混亂」。唯一的跨面板規則（從名片寄信：看板關、收件匣開）寫死在那一條路上。

## 選項

### A. 每條路各自處理（今天）
- 好：不加東西
- 壞：n 個面板 n² 條路；新面板（`FE-J03`、`FE-K05`）進來又要各寫一次；沒有人守「同時只有一個」

### B. 網址決定開哪個
- 好：可深連結、可回上一頁
- 壞：收件匣與名片不在網址裡（`FE-B09` 只同步看板），塞進去是 `FE-B09` 的規格變更；送出中拒絕關閉跟網址列打架

### C. 一個協調者，provider 向它登記（選這個）
- 好：「同時只有一個」是協調者看得到的事實（掛載中的殼登記）；讓位是兩個**同步**函式 `canYield()`／`yield()`，拒絕有回饋；非阻斷的表面只讀
- 壞：多一個 context；殼多兩個 prop；provider 開面板要先 `requestOpen()`；讓位不替使用者回答「要放棄修改嗎」（直接算拒絕）

## 決定

選 C。殼掛載時登記 `{ id, canYield, yield }`（卸載釋放、冪等）；開面板前 `requestOpen(id)`（同步、原子：成功就**保留**給那個 id，殼登記時解除；保留期間別的 id 拒絕 —— 同一次事件兩個請求只有第一個贏）：沒有持有者 → 開；`canYield()` → `yield()`（走既有關閉路徑、不還焦點）後開；
否則拒絕：不開、持有者留著、`role="status"` 回饋。下一頁的 `restore`（讓位是 `go(-1)`，看板那一筆在前進紀錄）也經過它，被拒 → `replaceState` 目前這一筆回實際狀態、不 push。
第一版寫「呼叫 `onCloseRequest()` 看它接不接受」—— 那是 `() => void`，同步拿不到答案；兩個審查者同時抓到，改成上面這樣。
非阻斷的表面（訪客提示、聊天框、彈出層）**只讀不登記**。

## 代價

多一個 context、殼多兩個 prop、一次同步的 `requestOpen()`；面板開著時看不到聊天內容（收成一行＋新訊息數）；名片有未儲存修改時別的入口按了沒反應（有回饋，但要先自己處理）。

## 什麼情況下要重新考慮

- 要讓兩個面板並排（例如看板＋收件匣同時開）—— 那是版面決策，不是加一個例外
- 收件匣或名片要能深連結 —— 改走 B，`FE-B09` 重開規格
- 讓位需要問使用者（非同步）—— 那時 `canYield` 要變成 Promise，整個協定要重寫
