# 0001. 後端合約用引用的，不複述

- **Status**: Accepted
- **Date**: 2026-09-04

## 背景

後端（`GuildHub-backend`）已經存在，而且合約是定義好的：

| 東西 | 真實來源 |
|---|---|
| REST 欄位與型別 | `http://localhost:8000/docs`（OpenAPI，**自動產生**） |
| WebSocket 協定 | `app/realtime/protocol.py`（**手寫，但它就是規格本身**） |

後端自己的整合指南也是這樣定的：

> 欄位層級的真實來源是 `/docs`，不是這份文件⋯⋯欄位名稱與型別若與 `/docs`
> 不一致，**以 `/docs` 為準**，並回報給後端。

問題是本 repo 的 `docs/ROADMAP.md` 與 `docs/WBS.md` 是**在後端存在之前寫的**，
描述的即時層與實際協定對不上至少七處 —— 訊息名稱、座標軸、朝向的表示法、
以及四件完全沒提到的行為（自己的 move 會回來、握手失敗不給 err、
狀態超長靜默丟棄、一連線一 scene）。

那七處不是小差異。照 WBS 寫規格，會寫出一份**在錯的前提上正確**的規格。

## 決定

**前端的規格與程式碼引用後端合約，不複述它。**

具體：

1. **REST 的型別用產的**，不手寫：
   ```bash
   npx openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts
   ```
   手寫的 interface 是複述，會漂。

2. **WS 的訊息型別**在前端只定義一次，而且要標明它對應
   `protocol.py` 的哪一段。後端改了那個檔案，前端的對應處要跟著改 ——
   **這是已知的手動同步點，寫出來比假裝沒有好。**

3. **規格（`openspec/changes/*/specs/`）寫行為與驗收條件，不列欄位表。**
   「收到 `pos` 之後遠端角色要在 100ms 內平滑移動到新位置」是行為；
   「`pos` 的格式是 `{"t":"pos","p":[[id,x,y,f]]}`」是欄位，指過去就好。

4. `CONTEXT.md` 記的是**對不上的地方**與**會讓人以為壞掉的行為**，
   不是完整的協定抄本。

## 為什麼不複述

**複述一定會漂，而漂掉的合約比沒有合約危險** —— 讀的人會相信它。

這個 repo 在同一天之內示範過三次：`README` 寫著「沒有人類批准的閘門」
而 ruleset 已經要求批准、`DECISIONS.md` 自己警告「數字會漂」卻寫死了案例數、
`CLAUDE.md` 半抄了 chore 的規則然後規則長出新條款。

三次都是同一個形狀：**在兩個地方描述同一件事**。

## 代價

- **WS 的型別是手動同步點。** 沒有 codegen（WS 沒有 OpenAPI）。
  後端改 `protocol.py` 而前端沒跟上，不會有任何機制告訴我們 ——
  只會在執行期收到不認得的訊息。緩解：Zod 驗證所有進來的訊息，
  收到不認得的 `t` 要**明顯地失敗**，不要靜默忽略。
- **需要後端跑著才能產 REST 型別。** CI 不會有後端，所以
  `src/api/schema.d.ts` 要進版控，並在 PR 描述註明是用哪個版本產的。

## 沒有選的替代方案

**把後端合約抄一份進前端的規格。** 好處是 review 的人不必開另一個 repo。
代價是兩份會漂，而且漂了沒有人會發現 —— 見上面那三次。

**共用一個 schema 套件。** 兩個 repo、兩種語言（Python / TypeScript），
現階段建立那個管線的成本大於收益。等到手動同步真的出事一次再考慮。
