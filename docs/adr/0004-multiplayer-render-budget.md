# 0004. 40 人同畫面的渲染預算判定

- **Status**: Accepted
- **Date**: 2026-09-09
- **Deciders**: FE-R09（規格 `openspec/specs/load-budget/`）

## 背景

`CONTEXT.md`：**「40 人同畫面是架構決定，不是收尾優化。」**

`FE-R09` 是 W1 的 Go / No-Go 閘門。答案是「不行」的話，`FE-W13` 渲染預算、
`FE-W08` ProceduralAvatar、`FE-V05` 群體訊號全部要重新設計。

工作分解表要求「40 個真實 Chromium」。那件事在這台機器上做不到 ——
量出來的：一個 headless Chromium 跑**空白的** WebGL 頁面就要 225 MB
（1／2／3／4 個合計 260／485／692／902 MB），40 × 225 = 9 GB
超過整台機器的實體記憶體（8 GB）。

所以拆成兩半量：伺服器／協定，以及單一前端的渲染。

## 量到的數字

### 伺服器與協定：40 條連線完全沒有衰減

```
40 個 WebSocket client／15 秒／不開任何瀏覽器

每個 client 收到的 pos 則數：中位數 150　p99 150　最少 150
平均每秒 10.0 則（後端 HZ 是 10）
中途斷線：0
全部靜止 3 秒之後收到的 pos：0
```

**`p99` = 中位數 = 最少。** 沒有離散、沒有掉線、靜止時不送。

### 單一前端：39 個遠端角色，純軟體渲染下 24 FPS

```
SwiftShader（無 GPU）

  N     FPS    幀間隔中位數   p99
  0    41.4      16.7 ms     33.4
  5    35.8      33.3        50
  20   29.9      33.3        66.6
  39   24.4      33.4        66.8
```

**沒有懸崖，是平緩下降。**

### 假流量的品質會改變結論

```
N=39            FPS #1   FPS #2   p99 #1   p99 #2
有抖動＋突發      27.5     23.3     66.6     133.4 ms
乾淨（對照組）    31.0     30.6     66.7     50.1
```

送得太漂亮的假 client 會把 FPS **高報約 20%**，而且完全看不到那個 133 ms 的長幀。

## 決定

**Go。** 40 人同畫面在架構上成立，`FE-W13` 不必為了「能不能做到」而改設計。

**理由**：伺服器端零衰減；前端在**沒有 GPU** 的情況下 39 人還有 24 FPS，
而且從 0 到 39 是平緩下降不是懸崖。真實使用者有 GPU，數字只會更好。

**這不表示不需要 `FE-W13`。** 它需要的是**數字目標**，而不是「能不能做到」的答案：

- `ChibiPlayer` 目前每個實例宣告自己的 9 份 geometry ＋ 9 份 material，
  40 人就是 360 對（`FE-W07` 的 D6 記過這件事）
- 上面的 24 FPS 是**現在這個實作**的數字，不是上限

## 代價

- **這個 Go 不涵蓋「40 個完整前端在同一台機器上」。** 那需要 40 個真實瀏覽器，
  而這台機器跑不動。量不到的東西：多個瀏覽器搶同一顆 GPU、每個玩家自己的
  本地角色成本、真實客戶端的載入與 shader 編譯尖峰、時鐘漂移
- 數字是 SwiftShader 的。真實 GPU 上的分佈形狀可能不同 ——
  **平緩下降這個性質**比 24 這個數字重要
- 假 client 不是真實玩家。它的抖動與突發是模擬的，而模擬的參數是猜的

## 什麼情況下要重新考慮

- **有 GPU 的機器可用時**：重量一次，那時的數字才是給使用者的
- **`FE-W08` 換成正式的 Avatar 之後**：現在的角色是九個方塊，正式版更重
- **每個角色開始有名字、狀態文字、互動提示之後**（`FE-W08`／`FE-V07`）：
  那些是 DOM 或額外的 draw call，不在這次的量測裡
- **`N` 超過 40**：這次只量到 39。線性外推是猜的
